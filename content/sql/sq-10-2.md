## 시작하기 전에

[한 사실은 한 곳에: 이상 현상과 정규화](#/l/sq-10-1)에서 표를 나눠 중복과 이상 현상을 없앴습니다. 대신 대가가 하나 생겼습니다. 원래 명단 하나를 보려고 표 네 개를 JOIN해야 했죠. 이번 레슨에서는 그 대가를 줄이려고 **일부러 다시 합치는** 반정규화와, 분석용 데이터베이스가 어떻게 설계되는지 배웁니다.

- 반정규화가 필요한 이유와 대표 기법
- 반정규화의 위험: 원본과 사본이 어긋난다
- 주문을 처리하는 DB(OLTP)와 분석하는 DB(OLAP)
- 스타 스키마: 팩트 표와 디멘전 표

## 정규화의 대가: 질문마다 JOIN

쇼핑몰 데이터는 정규화되어 있습니다. 주문 표에는 고객 번호만 있고, 가입 경로(검색 · SNS · 추천)는 고객 표에 있습니다. 그래서 "가입 경로별 매출"을 보려면 매번 JOIN해야 합니다.

```sqlrun
SELECT u.channel, COUNT(*) AS n_orders, SUM(o.amount) AS revenue
FROM orders o
JOIN users u ON o.user_id = u.user_id
GROUP BY u.channel;
```

검색 고객의 매출이 약 957만 원으로 가장 큽니다. 주문 372건이면 순식간이지만, 주문이 하루 수백만 건씩 쌓이는 회사에서 대시보드를 열 때마다 큰 표끼리 JOIN하고 몇 년 치를 다시 더하면 화면이 한참 걸립니다.

## 반정규화: 읽기 위해 일부러 중복을 허용

**반정규화**(Denormalization)는 조회를 빠르고 단순하게 하려고 **정규화 규칙을 일부러 어기는 것**입니다. 대표적인 방법은 세 가지입니다.

| 기법 | 하는 일 | 예 |
| --- | --- | --- |
| **중복 열 추가** | 자주 JOIN해서 가져오는 열을 미리 복사해 둔다 | 주문 표에 고객의 가입 경로 · 지역을 함께 저장 |
| **집계(요약) 테이블** | 매번 계산하는 합계를 미리 계산해 표로 저장 | 월별 매출 표, 일별 방문자 표 |
| **테이블 합치기** | 늘 같이 쓰는 1:1 · 1:N 표를 하나로 | 주문 + 주문 상세를 한 표로 |

### 중복 열: 주문 표에 가입 경로를 복사

`CREATE TABLE … AS SELECT …`는 SELECT 결과를 그대로 새 표로 저장합니다. 주문에 고객의 가입 경로와 지역을 붙인 "넓은 주문 표"를 만들어 봅니다.

```sqlrun
CREATE TABLE orders_wide AS
SELECT o.order_id, o.user_id, o.order_date, o.category, o.amount, u.channel, u.city
FROM orders o
JOIN users u ON o.user_id = u.user_id;

SELECT channel, COUNT(*) AS n_orders, SUM(amount) AS revenue
FROM orders_wide
GROUP BY channel;
```

결과는 앞의 JOIN 쿼리와 똑같은데, 이번에는 **JOIN 없이** 한 표에서 바로 묶었습니다. 분석가 입장에서는 쿼리가 짧아지고 DB 입장에서는 일이 줄어듭니다.

### 위험: 원본과 사본이 어긋난다

공짜는 없습니다. 57번 고객의 가입 경로 기록이 잘못되어 고객 표를 'SNS'로 고쳤다고 해 봅시다. 넓은 주문 표에는 예전 값이 복사되어 있습니다.

```sqlrun
CREATE TABLE orders_wide AS
SELECT o.order_id, o.user_id, o.amount, u.channel
FROM orders o JOIN users u ON o.user_id = u.user_id;

UPDATE users SET channel = 'SNS' WHERE user_id = 57;

SELECT w.order_id, w.channel AS wide_channel, u.channel AS users_channel
FROM orders_wide w
JOIN users u ON w.user_id = u.user_id
WHERE w.user_id = 57;
```

같은 고객인데 고객 표는 'SNS', 넓은 주문 표 7줄은 여전히 '추천'입니다. [한 사실은 한 곳에: 이상 현상과 정규화](#/l/sq-10-1)에서 본 **갱신 이상이 그대로 돌아왔습니다.** 이 상태로 "가입 경로별 매출"을 두 사람이 서로 다른 표에서 뽑으면 숫자가 달라지고, 회의는 "누구 숫자가 맞나"로 흘러갑니다.

### 집계 테이블: 미리 더해 둔 월별 매출

대시보드가 매번 보는 월별 매출을 미리 계산해 둡니다.

```sqlrun
CREATE TABLE monthly_sales AS
SELECT substr(order_date, 1, 7) AS month, COUNT(*) AS n_orders, SUM(amount) AS revenue
FROM orders
GROUP BY month;

SELECT * FROM monthly_sales;
```

7행짜리 작은 표라 대시보드는 이 표만 읽으면 됩니다. 원본이 수억 행이어도 요약 표는 몇 줄입니다. 그런데 요약 표를 만든 **뒤에** 주문이 하나 더 들어오면 어떻게 될까요?

```sqlrun
CREATE TABLE monthly_sales AS
SELECT substr(order_date, 1, 7) AS month, SUM(amount) AS revenue
FROM orders
GROUP BY month;

INSERT INTO orders (order_id, user_id, order_date, category, amount)
VALUES (99999, 57, '2025-07-31', '전자', 1000000);

SELECT m.month, m.revenue AS summary_revenue,
       (SELECT SUM(amount) FROM orders WHERE substr(order_date, 1, 7) = '2025-07') AS actual_revenue
FROM monthly_sales m
WHERE m.month = '2025-07';
```

요약 표는 205만 원, 실제 주문 합계는 305만 원입니다. 요약 표는 **만든 순간의 사진**이라 원본이 바뀌어도 저절로 따라가지 않습니다. 그래서 실무에서는 "매일 새벽 3시에 다시 계산한다" 같은 **갱신 규칙**을 꼭 함께 정하고, 대시보드에 "기준 시각"을 표시합니다.

> 대시보드 숫자가 원본 쿼리와 다르면, 가장 먼저 "이 요약 표가 언제 갱신됐지?"를 확인하세요. 실무에서 가장 흔한 숫자 불일치 원인입니다.

## 반정규화의 순서와 규칙

반정규화는 "JOIN이 귀찮으니 처음부터 합쳐 두자"가 아닙니다.

1. **정규화를 먼저** 끝낸다(보통 3NF).
2. 실제로 느린 쿼리와 자주 쓰는 질문을 **측정**한다.
3. 인덱스나 쿼리 개선으로 해결되지 않을 때만, 꼭 필요한 곳을 반정규화한다.
4. 중복 데이터를 **누가, 언제, 어떻게 맞출지** 규칙을 정한다.

| | 정규화 | 반정규화 |
| --- | --- | --- |
| 목적 | 중복 · 이상 현상 제거, 일관성 | 조회 속도, 쿼리 단순화 |
| 대가 | JOIN이 늘어남 | 중복 저장, 원본과 어긋날 위험, 쓰기 비용 |
| 언제 | 논리 설계의 기본 | 물리 설계에서, 측정된 병목에만 |

## 처리용 DB와 분석용 DB

회사에는 보통 성격이 다른 데이터베이스가 두 종류 있습니다.

| | OLTP (온라인 트랜잭션 처리) | OLAP (온라인 분석 처리) |
| --- | --- | --- |
| 하는 일 | 주문 접수, 결제, 회원 가입 | 매출 분석, 대시보드, 리포트 |
| 쿼리 모양 | 한 건씩 넣고 고치기 (INSERT · UPDATE) | 수백만 행을 묶어 더하기 (GROUP BY) |
| 설계 | **정규화** (쓰기가 정확해야 함) | **반정규화** (읽기가 빨라야 함) |
| 예 | MySQL · PostgreSQL로 만든 서비스 DB | 데이터 웨어하우스: BigQuery · Snowflake · Redshift |

서비스 DB(OLTP)에서 매일 데이터를 옮겨 분석하기 좋은 모양으로 바꿔 데이터 웨어하우스(OLAP)에 쌓는 작업을 **ETL**(추출 · 변환 · 적재)이라고 합니다. 데이터 분석가가 실제로 쿼리하는 곳은 대부분 이 분석용 DB입니다.

## 스타 스키마: 분석용 설계의 기본형

분석용 DB에서 가장 많이 쓰는 모양이 **스타 스키마**(Star Schema)입니다. 가운데에 사건을 기록한 **팩트 표**가 있고, 주변에 그 사건을 설명하는 **디멘전 표**가 별 모양으로 붙습니다.

- **팩트(Fact) 표**: 측정할 숫자가 있는 사건 기록. 주문 한 건, 방문 한 번. 행이 아주 많고, 금액 · 수량 같은 **측정값**과 디멘전을 가리키는 키로 이루어집니다.
- **디멘전(Dimension) 표**: "누가 · 언제 · 무엇을 · 어디서"를 설명하는 표. 고객 · 날짜 · 상품 · 지역. 행은 적고, 분석할 때 **묶는 기준**(GROUP BY에 들어갈 열)이 됩니다.

디멘전 표는 일부러 정규화하지 않습니다. 예를 들어 `dim_product`에 분류 이름을 반복해서 적어 두면, 팩트와 JOIN 한 번이면 "분류별 매출"이 나옵니다. 디멘전까지 정규화해 여러 층으로 쪼갠 모양은 눈송이처럼 생겨서 **스노우플레이크 스키마**라고 부릅니다.

Tableau나 Power BI 같은 BI 도구도 이 구조를 전제로 만들어져 있습니다. 대시보드를 만들 때 "측정값(Measure)"과 "차원(Dimension)"을 나누는 것이 바로 팩트와 디멘전입니다.

## 정리

- 반정규화 = 조회를 위해 일부러 중복을 허용. 중복 열 · 집계 테이블 · 테이블 합치기.
- 대가는 **원본과 사본이 어긋날 위험**. 갱신 규칙과 기준 시각을 함께 정한다.
- 순서는 언제나 정규화 먼저, 측정 후 꼭 필요한 곳만 반정규화.
- 처리용 DB(OLTP)는 정규화, 분석용 DB(OLAP · 데이터 웨어하우스)는 반정규화.
- 스타 스키마: 사건과 숫자는 팩트 표, 묶는 기준은 디멘전 표.
