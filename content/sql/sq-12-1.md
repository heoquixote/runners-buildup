## 시작하기 전에

[데이터 넣고 고치고 지우기](#/l/sq-11-2)에서 INSERT · UPDATE · DELETE를 배웠습니다. 그런데 현실의 작업은 명령 하나로 끝나지 않는 경우가 많습니다. 송금은 "내 통장에서 빼기"와 "친구 통장에 더하기" 두 번의 UPDATE입니다. 그 사이에 문제가 생기면 어떻게 될까요?

- 트랜잭션: 여러 명령을 "한 덩어리"로 묶기
- BEGIN · COMMIT · ROLLBACK
- ACID: 트랜잭션이 지키는 네 가지 약속
- 여러 사람이 동시에 쓸 때: 잠금

## 송금 중에 정전이 나면

민준(100원)이 서연(50원)에게 70원을 보냅니다. 은행 DB는 두 번 고칩니다. 첫 번째 UPDATE가 끝난 순간 서버가 꺼졌다고 해 봅시다.

```sqlrun
CREATE TABLE account (owner TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
INSERT INTO account VALUES ('민준', 100), ('서연', 50);

UPDATE account SET balance = balance - 70 WHERE owner = '민준';
-- 여기서 정전! 서연에게 더하는 UPDATE는 실행되지 못했다

SELECT owner, balance FROM account;
SELECT SUM(balance) AS total FROM account;
```

민준의 돈은 빠졌는데(30원) 서연은 그대로(50원)입니다. 두 사람 잔액의 합이 150원에서 **80원**이 되었습니다. 70원이 허공으로 사라졌습니다. 순서를 바꿔 더하기를 먼저 했다면 반대로 돈이 **생겨났겠죠**. 어느 쪽이든 은행은 문을 닫아야 합니다.

## 트랜잭션: 한 덩어리로 묶기

**트랜잭션**(Transaction)은 "모두 성공하거나, 모두 없던 일이 되어야 하는" 작업 묶음입니다. SQL로는 세 명령으로 다룹니다.

- `BEGIN` (MySQL은 `START TRANSACTION`): 지금부터 한 덩어리 시작
- `COMMIT`: 지금까지의 변경을 **확정**. 이후로는 되돌릴 수 없음
- `ROLLBACK`: 지금까지의 변경을 **모두 취소**하고 BEGIN 직전으로

ROLLBACK부터 해 봅니다. 송금 두 UPDATE를 한 뒤, 확정하지 않고 취소합니다.

```sqlrun
CREATE TABLE account (owner TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
INSERT INTO account VALUES ('민준', 100), ('서연', 50);

BEGIN;
UPDATE account SET balance = balance - 70 WHERE owner = '민준';
UPDATE account SET balance = balance + 70 WHERE owner = '서연';
SELECT owner, balance FROM account;
ROLLBACK;

SELECT owner, balance FROM account;
```

결과 표가 두 개입니다. 첫 번째(ROLLBACK 전)는 30원 · 120원으로 송금이 된 것처럼 보이지만, 두 번째(ROLLBACK 후)는 100원 · 50원 **원래대로**입니다. ROLLBACK이 BEGIN 이후의 모든 변경을 한 번에 지웠습니다.

> 직접 해보기: `ROLLBACK;`을 `COMMIT;`으로 바꿔 실행해 보세요. 두 번째 표도 30원 · 120원이 됩니다. COMMIT 뒤에는 ROLLBACK을 해도 되돌아가지 않습니다.

## 오류가 나면 되돌리기

이번에는 민준이 가진 것보다 많은 200원을 보내려 합니다. 잔액은 0 이상이어야 한다는 `CHECK`가 걸려 있습니다. 서연에게 더하기는 성공하고, 민준에게서 빼기에서 막힙니다.

```sqlrun
-- 오류 예시
CREATE TABLE account (owner TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
INSERT INTO account VALUES ('민준', 100), ('서연', 50);

BEGIN;
UPDATE account SET balance = balance + 200 WHERE owner = '서연';
UPDATE account SET balance = balance - 200 WHERE owner = '민준';
COMMIT;
```

5번째 문장(민준 −200)에서 `CHECK constraint failed`가 나고 COMMIT까지 가지 못했습니다. 이때 서연의 +200은 아직 확정되지 않은 상태입니다. 은행 프로그램은 오류를 받으면 `ROLLBACK`을 보내 서연의 +200까지 취소합니다. 그래서 "돈이 생겨나는" 일이 없습니다. 트랜잭션과 제약조건이 함께 일하는 모습입니다. (이 사이트의 셀은 오류가 나면 거기서 멈추고 그 DB를 버리기 때문에, 결과적으로 ROLLBACK과 같습니다.)

> 이 사이트와 DBeaver · MySQL Workbench는 기본으로 **자동 커밋**(autocommit) 모드입니다. BEGIN 없이 쓴 UPDATE는 실행 즉시 확정됩니다. 회사 DB에서 중요한 데이터를 고칠 때는 BEGIN으로 감싸고, [데이터 넣고 고치고 지우기](#/l/sq-11-2)의 "SELECT로 먼저 확인 → 바꾸기 → 행 수 비교" 후에 COMMIT하는 습관을 들이세요.

## ACID: 트랜잭션의 네 가지 약속

데이터베이스는 트랜잭션에 대해 네 가지를 약속합니다. 머리글자를 따서 **ACID**라고 합니다.

| 약속 | 뜻 | 송금 예 |
| --- | --- | --- |
| **원자성** (Atomicity) | 전부 되거나 전부 안 된다. 쪼갤 수 없는 원자처럼 | 빼기만 되고 더하기는 안 되는 일은 없다 |
| **일관성** (Consistency) | 트랜잭션 전후로 규칙(제약조건)이 지켜진다 | 잔액은 늘 0 이상, 두 사람 합계는 그대로 |
| **격리성** (Isolation) | 동시에 실행되는 트랜잭션이 서로의 중간 상태를 보지 않는다 | 송금 도중에 잔액을 조회한 사람이 "반쯤 보낸" 잔액을 보지 않는다 |
| **지속성** (Durability) | COMMIT된 결과는 정전이 나도 남는다 | "송금 완료" 문자를 받았으면 서버가 꺼져도 송금은 유지 |

원자성은 ROLLBACK이, 일관성은 제약조건이, 지속성은 DB가 COMMIT 전에 변경 기록(로그)을 디스크에 먼저 써 두는 방식이 지킵니다. 격리성은 다음 절의 **잠금**이 지킵니다.

## 여러 사람이 동시에 쓸 때: 잠금

공연 좌석 예매를 생각해 봅시다. 마지막 남은 51번 좌석을 A와 B가 **동시에** 확인합니다. 둘 다 "비어 있음"을 보고 둘 다 예매하면, 한 좌석이 두 번 팔립니다.

DB는 이를 **잠금**(Lock)으로 막습니다. A의 트랜잭션이 51번 좌석 행을 고치기 시작하면 그 행에 자물쇠를 채우고, B는 A가 COMMIT(또는 ROLLBACK)해서 자물쇠가 풀릴 때까지 **기다립니다.** 풀린 뒤 B가 다시 보면 이미 팔린 좌석입니다.

잠금은 안전하지만 기다림을 만듭니다. 그래서 트랜잭션은 **짧게** 유지하는 것이 원칙입니다. BEGIN 해 놓고 점심 먹으러 가면, 그동안 그 행을 고치려는 다른 사람들이 모두 멈춥니다. 데이터 분석가가 운영 DB에 무거운 쿼리를 오래 돌리면 서비스가 느려지는 것도 같은 이유입니다. 분석은 분석용 DB에서 하는 것이 원칙입니다.

> 격리성을 얼마나 엄격하게 지킬지는 **격리 수준**(Isolation Level)으로 고릅니다. 가장 엄격한 SERIALIZABLE은 안전하지만 느리고, 느슨할수록 빠르지만 "아직 COMMIT 안 된 값을 읽는"(Dirty Read) 같은 현상이 생길 수 있습니다. MySQL의 기본값은 REPEATABLE READ입니다.

## 정리

- 트랜잭션 = 모두 되거나 모두 안 되어야 하는 작업 묶음.
- `BEGIN` → 변경들 → `COMMIT`(확정) 또는 `ROLLBACK`(전부 취소).
- 오류가 나면 ROLLBACK해서 중간 상태를 남기지 않는다.
- ACID: 원자성 · 일관성 · 격리성 · 지속성.
- 동시에 같은 데이터를 고치면 잠금으로 줄을 세운다. 그래서 트랜잭션은 짧게.
