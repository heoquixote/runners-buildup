## 책 뒤의 찾아보기

두꺼운 교과서에서 "정규화"가 나오는 쪽을 찾으려면 어떻게 하나요? 첫 쪽부터 한 장씩 넘기면 확실하지만 오래 걸립니다. 그래서 책 맨 뒤에 가나다순으로 정리된 **찾아보기**(색인)를 펴서 "정규화 … 214쪽"을 보고 바로 넘어갑니다.

데이터베이스의 **인덱스**(Index)가 바로 이 찾아보기입니다. 인덱스가 없으면 DB는 조건에 맞는 행을 찾으려고 표의 **처음부터 끝까지** 다 읽습니다(Full Scan, 전체 스캔). 인덱스가 있으면 정렬된 찾아보기를 따라 내려가서 해당 행의 위치로 바로 갑니다.

대부분의 DB 인덱스는 **B-Tree**(균형 트리) 구조입니다. 값을 정렬해 두고 "이 범위는 왼쪽, 저 범위는 오른쪽"으로 나눠 내려가므로, 100만 행이어도 몇 단계 만에 원하는 위치에 닿습니다. 스무고개에서 "50보다 커?"를 반복하면 금방 맞히는 것과 같은 원리입니다.

## 실행 계획: DB가 어떻게 찾을지 물어보기

쿼리 앞에 `EXPLAIN QUERY PLAN`을 붙이면, 결과 대신 **DB가 그 쿼리를 어떻게 실행할지**(실행 계획)를 보여 줍니다. 방문 기록에서 7번 고객의 행을 찾는 쿼리를 물어봅니다.

```sqlrun
EXPLAIN QUERY PLAN
SELECT * FROM events WHERE user_id = 7;
```

`detail` 칸에 **SCAN events**라고 나옵니다. "events를 처음부터 끝까지 훑겠다"는 뜻입니다. `user_id`에 인덱스가 없으니 다른 방법이 없습니다. 이제 인덱스를 만들고 같은 질문을 합니다.

```sqlrun
CREATE INDEX idx_events_user ON events (user_id);

EXPLAIN QUERY PLAN
SELECT * FROM events WHERE user_id = 7;
```

**SEARCH events USING INDEX idx_events_user (user_id=?)**로 바뀌었습니다. "인덱스를 써서 user_id가 같은 곳으로 바로 찾아가겠다"는 뜻입니다. `CREATE INDEX 인덱스이름 ON 표 (열)`이 인덱스를 만드는 DDL입니다. 이름은 보통 `idx_표_열`로 짓습니다.

> 쿼리를 하나도 고치지 않았다는 점이 중요합니다. 인덱스를 쓸지 말지는 DB의 **옵티마이저**(실행 계획을 고르는 두뇌)가 알아서 정합니다. SQL이 "무엇을"만 적는 언어라서 가능한 일입니다. MySQL에서는 `EXPLAIN SELECT …`로 실행 계획을 봅니다.

기본키에는 인덱스가 저절로 만들어집니다. 주문 번호로 찾으면 인덱스를 만들지 않아도 SEARCH가 나옵니다.

```sqlrun
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE order_id = 10053;
```

`SEARCH orders USING INTEGER PRIMARY KEY`. 기본키와 UNIQUE 열은 "겹치는지" 검사하려면 빨리 찾아야 하니, DB가 알아서 인덱스를 붙입니다.

## 여러 열 인덱스는 순서가 중요

인덱스는 열 여러 개로도 만듭니다(**복합 인덱스**). 그런데 열 순서가 중요합니다. 전화번호부는 "성 → 이름" 순으로 정렬되어 있어서 "김씨 중 민준"은 빨리 찾지만, 성을 모르고 "이름이 민준인 사람"만 찾으려면 처음부터 다 봐야 하죠.

```sqlrun
CREATE INDEX idx_orders_user_date ON orders (user_id, order_date);

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE user_id = 7 AND order_date >= '2025-03-01';

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE order_date >= '2025-07-01';
```

첫 번째는 (고객, 날짜) 인덱스를 써서 SEARCH, 두 번째는 날짜만으로 찾으니 **SCAN**입니다. 인덱스의 첫 열(`user_id`)이 조건에 없어서 정렬 순서를 활용할 수 없기 때문입니다. 그래서 복합 인덱스는 **WHERE에 항상 들어가는 열, 같다(=)로 찾는 열을 앞에** 둡니다.

## 인덱스를 못 쓰게 만드는 조건

인덱스가 있어도 조건을 쓰는 방식 때문에 못 쓰는 경우가 있습니다. 가장 흔한 실수는 **인덱스 열에 함수를 씌우는 것**입니다. 날짜 인덱스를 만들고 7월 주문을 두 가지 방법으로 찾아봅니다.

```sqlrun
CREATE INDEX idx_orders_date ON orders (order_date);

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE substr(order_date, 1, 7) = '2025-07';

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE order_date >= '2025-07-01' AND order_date < '2025-08-01';
```

두 쿼리의 결과 행은 똑같지만, `substr(order_date, …)`처럼 열을 함수로 감싸면 **SCAN**, 열을 그대로 두고 범위로 쓰면 **SEARCH**입니다. 인덱스에는 `order_date` 값이 정렬되어 있지, `substr(order_date, 1, 7)`의 결과가 정렬되어 있지는 않기 때문입니다. 찾아보기는 "정규화"로 정리되어 있는데 "규화"로 끝나는 단어를 찾는 셈입니다.

인덱스를 못 쓰게 되는 대표적인 경우:

| 조건 | 왜 | 대신 |
| --- | --- | --- |
| `WHERE substr(order_date, 1, 7) = '2025-07'` | 열을 함수로 감쌈 | `order_date >= '2025-07-01' AND order_date < '2025-08-01'` |
| `WHERE sal * 12 > 100000` | 열에 계산을 함 | `sal > 100000 / 12` |
| `WHERE name LIKE '%준'` | 앞이 `%`라 시작 글자를 모름 | `LIKE '민%'`처럼 앞을 고정 (MySQL) |
| 복합 인덱스의 첫 열이 없는 조건 | 정렬 순서를 못 씀 | 인덱스 열 순서 조정 |

## 인덱스는 공짜가 아니다

그럼 모든 열에 인덱스를 만들면 될까요? 아닙니다.

| 장점 | 비용 |
| --- | --- |
| WHERE · JOIN · ORDER BY가 빨라짐 | 인덱스도 따로 저장 공간을 차지 |
| UNIQUE 검사가 빨라짐 | INSERT · UPDATE · DELETE 때마다 인덱스도 고쳐야 해서 **쓰기가 느려짐** |
| | 너무 많으면 옵티마이저가 고를 경우의 수가 늘고 관리가 어려움 |

책에 찾아보기를 100개 붙이면 새 쪽을 끼울 때마다 찾아보기 100개를 모두 고쳐야 하는 것과 같습니다. 또 **값의 종류가 적은 열**(성별처럼 둘뿐인 열)은 인덱스로 찾아도 절반을 읽어야 해서 효과가 적습니다. 그래서 인덱스는 "자주 실행되는 느린 쿼리의 WHERE · JOIN 열"을 골라 만들고, 만든 뒤에는 실행 계획으로 정말 쓰이는지 확인합니다.

## 뷰: 쿼리에 이름 붙여 두기

[매출 · 퍼널 · 리텐션 표 만들기](#/l/sq-08-1)에서 만든 월별 KPI 쿼리처럼, 자주 쓰는 긴 쿼리가 있습니다. 매번 복사해 붙이는 대신 **이름을 붙여 저장**해 둘 수 있습니다. 이것이 **뷰**(View)입니다.

```sqlrun
CREATE VIEW monthly_kpi AS
SELECT substr(order_date, 1, 7) AS month,
       COUNT(*) AS n_orders,
       COUNT(DISTINCT user_id) AS buyers,
       SUM(amount) AS revenue
FROM orders
GROUP BY month;

SELECT * FROM monthly_kpi WHERE month >= '2025-05';
```

`CREATE VIEW 이름 AS SELECT …`로 만들고, 그다음부터는 **표처럼** `SELECT * FROM monthly_kpi`로 씁니다. WHERE도 JOIN도 됩니다. 뷰는 데이터를 따로 저장하지 않고 **쿼리만 저장**합니다. 조회할 때마다 원본 표에서 새로 계산하므로, [일부러 합치기: 반정규화와 분석용 테이블](#/l/sq-10-2)의 집계 테이블과 달리 원본과 어긋날 일이 없습니다. 대신 매번 계산하니 원본이 크면 느릴 수 있습니다.

뷰는 **보안**에도 씁니다. 사원 명단은 여러 사람이 봐야 하지만 연봉은 인사팀만 봐야 한다면, 연봉 열을 뺀 뷰를 만들어 그 뷰만 볼 권한을 줍니다(DCL의 GRANT).

```sqlrun
CREATE VIEW emp_public AS
SELECT empno, ename_ko, joblv, deptno
FROM emp
WHERE employed = 1;

SELECT * FROM emp_public;
```

재직자 13명의 이름 · 직급 · 부서만 보이고 연봉(`sal`)과 성과급(`comm`)은 없습니다.

| | 뷰 (View) | 집계 테이블 · 구체화 뷰 |
| --- | --- | --- |
| 저장하는 것 | 쿼리만 | 결과 데이터 |
| 원본과 일치 | 늘 최신 | 갱신할 때까지 옛날 값 |
| 속도 | 조회할 때마다 계산 | 미리 계산해 빠름 |
| 쓰는 곳 | 복잡한 쿼리 재사용, 보안 | 무거운 대시보드 |

> 결과를 저장해 두는 뷰를 **구체화 뷰**(Materialized View)라고 합니다. PostgreSQL · Oracle · BigQuery 등이 지원하고, 정해진 주기로 새로 계산(REFRESH)합니다. 뷰의 편리함과 집계 테이블의 속도를 합친 것입니다.

## 정리

- 인덱스 = 정렬된 찾아보기(B-Tree). 없으면 SCAN(전체 스캔), 있으면 SEARCH.
- `CREATE INDEX idx_표_열 ON 표 (열)`, 확인은 `EXPLAIN QUERY PLAN`(MySQL은 `EXPLAIN`).
- 복합 인덱스는 열 순서가 중요하고, 열에 함수 · 계산을 씌우면 인덱스를 못 쓴다.
- 인덱스는 읽기를 빠르게, 쓰기를 느리게 한다. 필요한 곳에만.
- 뷰 = 이름 붙인 SELECT. 재사용과 보안에 쓰고, 결과를 저장하는 것은 구체화 뷰.

이것으로 데이터베이스 설계 구역을 마칩니다. 개념 · 논리 · 물리 모델로 설계하고, 정규화로 나누고, 필요하면 반정규화하고, DDL과 제약조건으로 만들고, DML과 트랜잭션으로 안전하게 바꾸고, 인덱스와 뷰로 빠르고 편하게 읽는 흐름까지 왔습니다. 이제 처음 보는 데이터베이스를 받아도 "왜 표가 이렇게 나뉘어 있는지"부터 읽을 수 있습니다.
