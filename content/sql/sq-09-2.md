## 카디널리티: 관계의 모양

관계에는 모양이 있습니다. 이 모양을 **카디널리티**(Cardinality)라고 합니다. 두 엔터티 A, B 사이에서 질문을 **양쪽 방향으로 한 번씩** 던지면 알 수 있습니다.

1. "A 하나는 B 몇 개와 연결되나?"
2. "B 하나는 A 몇 개와 연결되나?"

| 모양 | 질문 답 | 예 |
| --- | --- | --- |
| **1:1** | 둘 다 "하나" | 사람 ↔ 여권, 사원 ↔ 사원증 |
| **1:N** (일대다) | 한쪽은 "여러 개", 반대쪽은 "하나" | 부서 → 사원, 고객 → 주문 |
| **N:M** (다대다) | 둘 다 "여러 개" | 학생 ↔ 과목, 주문 ↔ 상품 |

회사 데이터에서 확인해 봅니다. "부서 하나에 사원이 몇 명인가?"

```sqlrun
SELECT d.deptno, d.dname, COUNT(e.empno) AS n_emp
FROM dept d
LEFT JOIN emp e ON e.deptno = d.deptno
GROUP BY d.deptno, d.dname;
```

영업1팀은 5명, 영업2팀은 4명입니다. 반대로 "사원 한 명은 부서 몇 개에 속하나?"는 `emp` 표에 `deptno` 칸이 **하나뿐**이니 최대 하나입니다. 그래서 부서 : 사원 = **1 : N**입니다.

쇼핑몰의 고객과 주문도 봅니다. "고객 한 명은 주문이 몇 건인가?"

```sqlrun
SELECT user_id, COUNT(*) AS n_orders
FROM orders
GROUP BY user_id
ORDER BY n_orders DESC
LIMIT 5;
```

57번 고객은 7번 주문했습니다. 주문 한 건의 고객은 `user_id` 하나뿐이니 고객 : 주문 = **1 : N**입니다. 고객 256명 중 한 번도 사지 않은 64명도 있으니, 까마귀발로는 고객 쪽에서 "없거나 여러 개"(○ + 세 갈래)로 그립니다.

## 외래키는 N쪽에

1:N 관계를 표로 만들 때 **외래키는 N쪽(여러 개인 쪽) 표에** 둡니다. 사원 표에 `deptno`가 있고, 주문 표에 `user_id`가 있는 이유입니다.

반대로 1쪽에 두면 어떻게 될까요? 부서 표에 사원 번호를 적으려면 `emp1`, `emp2`, `emp3` … 칸을 몇 개 만들어야 할지 알 수 없고, 한 칸에 "1001, 1002, 1005"처럼 여러 값을 넣으면 검색도 집계도 안 됩니다. 사원 쪽에는 "내 부서" 칸 **하나**면 충분합니다. 시험에서는 **"외래키는 N쪽"**으로 외웁니다.

1:1 관계는 어느 쪽에 두어도 되고, 더 자주 찾아가는 쪽이나 값이 꼭 있는 쪽에 둡니다.

## N:M은 연결 테이블로

학생은 여러 과목을 듣고, 과목에도 여러 학생이 있습니다. 이 N:M 관계는 외래키 하나로 표현할 수 없습니다. 학생 표에 과목 칸을 두면 과목 수만큼 칸이 필요하고, 과목 표에 학생 칸을 두면 학생 수만큼 필요하니까요.

해결 방법은 둘 사이에 **연결 테이블**(교차 테이블)을 하나 끼워 넣는 것입니다. "누가 무엇을 들었다"를 한 줄씩 적는 수강 신청서 묶음을 떠올리면 됩니다. 그러면 N:M 하나가 **1:N 두 개**로 풀립니다.

직접 만들어 봅니다. 아래 셀은 표 세 개를 만들고(`CREATE TABLE`), 데이터를 넣고(`INSERT`), JOIN으로 "누가 무엇을 들었나"를 조회합니다. 표 만들기 문법은 [테이블 만들기: 자료형과 제약조건](#/l/sq-11-1)에서 자세히 배우니, 지금은 모양만 보세요.

```sqlrun
CREATE TABLE student (student_id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE course  (course_id TEXT PRIMARY KEY, title TEXT);
CREATE TABLE enroll  (student_id INTEGER, course_id TEXT, score INTEGER,
                      PRIMARY KEY (student_id, course_id));

INSERT INTO student VALUES (1, '민준'), (2, '서연'), (3, '도윤');
INSERT INTO course  VALUES ('DB', '데이터베이스'), ('ST', '통계'), ('PY', '파이썬');
INSERT INTO enroll  VALUES (1, 'DB', 90), (1, 'ST', 85), (2, 'DB', 78), (3, 'PY', 92), (3, 'DB', 88);

SELECT s.name, c.title, e.score
FROM enroll e
JOIN student s ON e.student_id = s.student_id
JOIN course  c ON e.course_id  = c.course_id
ORDER BY s.name;
```

결과 표의 한 줄이 "어떤 학생이 어떤 과목을 들었다"는 사실 하나입니다. 민준은 두 과목, 데이터베이스 과목에는 세 명이 있습니다. 양쪽 모두 "여러 개"인 관계가 연결 테이블 덕분에 깔끔하게 담겼습니다. 성적(`score`)이 학생 표도 과목 표도 아닌 **수강 표**에 있는 점도 보세요. "누가 어느 과목에서 받은" 점수라서 연결 테이블이 제자리입니다.

> 직접 해보기: `SELECT c.title, COUNT(*) FROM enroll e JOIN course c ON e.course_id = c.course_id GROUP BY c.title;`로 바꿔 과목별 수강생 수를 세어 보세요. 아무도 듣지 않는 과목까지 0으로 보려면 어떤 JOIN을 써야 할까요?

쇼핑몰의 "주문 ↔ 상품"도 전형적인 N:M입니다. 실제 쇼핑몰 DB에는 주문 한 건에 담긴 상품을 한 줄씩 적는 `order_items`(주문 상세) 연결 테이블이 거의 항상 있습니다. 이 사이트의 `orders`는 연습용이라 주문 한 건에 분류 하나만 적어 두었습니다.

## 키의 종류

[데이터베이스 구조와 첫 쿼리](#/l/sq-00-1)에서 기본키(PK)와 외래키(FK)를 한 줄로 만났습니다. 설계할 때는 키를 조금 더 세밀하게 나눕니다. 학생 표에 학번 · 주민번호 · 이메일 · 이름이 있다고 해 봅시다.

- **슈퍼키**: 행 하나를 콕 집을 수 있는(유일한) 열 묶음은 다 슈퍼키입니다. {학번}, {주민번호}, {학번, 이름}, {학번, 이메일, 이름} … 군더더기가 붙어 있어도 됩니다.
- **후보키**: 슈퍼키 중에서 군더더기가 없는 것. 열을 하나라도 빼면 더는 유일하지 않은 묶음입니다. {학번}, {주민번호}, {이메일}. 조건은 **유일성 + 최소성**입니다. {학번, 이름}은 이름을 빼도 학번만으로 유일하니 최소성이 없어 후보키가 아닙니다.
- **기본키**: 후보키 중에서 대표로 고른 하나. 비면 안 되고(NOT NULL) 겹치면 안 됩니다(UNIQUE). 보통 바뀌지 않고 짧은 것을 고릅니다 → {학번}
- **대체키**: 기본키로 뽑히지 못한 나머지 후보키 → {주민번호}, {이메일}
- **외래키**: 다른 표(또는 같은 표)의 기본키를 가리키는 열. 수강 표의 학번, 사원 표의 `deptno`

## 복합키, 그리고 자연키 vs 대리키

- **복합키**: 열 두 개 이상을 묶어 기본키로 쓰는 것. 앞의 수강 표는 학번 하나로도, 과목 코드 하나로도 행이 정해지지 않고 **(학번, 과목 코드)** 쌍이어야 하나로 정해집니다. 그래서 `PRIMARY KEY (student_id, course_id)`로 묶었습니다. 같은 학생이 같은 과목을 두 번 신청하는 실수도 이 키가 막아 줍니다.
- **자연키**: 원래 세상에 있던 값으로 만든 키(주민번호, 이메일, 차량 번호).
- **대리키**: 의미 없이 1, 2, 3 … 붙인 번호(`user_id`, `order_id`).

실무에서는 **대리키를 기본키로** 쓰는 경우가 많습니다. 이메일은 바뀔 수 있고, 주민번호는 개인정보라 여기저기 외래키로 복사하면 안 되기 때문입니다. 대신 자연키 열에는 겹치지 않도록 `UNIQUE` 제약을 걸어 둡니다.

## 정리

- ERD = 엔터티와 관계의 지도. Chen 표기(사각형 · 마름모 · 타원)와 까마귀발 표기(상자 + 선 끝 기호).
- 카디널리티는 양쪽 방향 질문으로 정한다: 1:1 · 1:N · N:M.
- 1:N의 외래키는 **N쪽**에, N:M은 **연결 테이블**로 1:N 두 개로 푼다.
- 슈퍼키 ⊃ 후보키(유일 + 최소) ⊃ 기본키, 나머지 후보키는 대체키. 외래키는 다른 표의 기본키를 가리킨다.
- 실무는 대리키(번호)를 기본키로, 자연키에는 UNIQUE.
