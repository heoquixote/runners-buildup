## 시작하기 전에

지금까지는 누군가 **이미 만들어 둔** 표(`emp` · `dept` · `orders` …)에서 데이터를 꺼냈습니다. 그런데 그 표들은 누가, 어떤 기준으로 나눠 만들었을까요? [흩어진 표를 키로 잇기](#/l/sq-04-1)에서 "부서 이름을 사원 표에 다 적으면 고칠 때 곤란하니 표를 나눴다"는 이야기를 잠깐 했습니다. 이번 구역에서는 그 반대편, **표를 설계하고 만드는 쪽**을 배웁니다.

이번 레슨에서 배울 것:

- 데이터 모델링이 무엇이고 왜 필요한지
- 엔터티 · 속성 · 관계
- 개념 모델 → 논리 모델 → 물리 모델, 세 단계가 각각 정하는 것

## 집을 지을 때처럼

집을 지을 때 바로 벽돌부터 쌓지 않습니다. 먼저 "방 3개, 거실 하나, 화장실 2개" 같은 **스케치**를 그리고, 다음에 방 크기와 문 위치를 정한 **평면도**를 그리고, 마지막에 벽 두께 · 자재 · 배관까지 적은 **시공도**를 만든 뒤에야 공사를 시작합니다. 공사가 끝난 뒤 "거실을 반대쪽으로 옮겨 주세요"라고 하면 집을 거의 다시 지어야 합니다.

데이터베이스도 같습니다. 표를 만들고 데이터가 수백만 줄 쌓인 뒤에 구조를 바꾸면, 그 표를 쓰는 프로그램 · 보고서 · 대시보드가 줄줄이 깨집니다. 그래서 표를 만들기 전에 **어떤 데이터를, 어떤 표로 나눠, 어떻게 연결할지** 설계도를 먼저 그립니다. 이 일을 **데이터 모델링(Data Modeling)**이라고 합니다.

## 엔터티 · 속성 · 관계

설계도를 그릴 때 쓰는 단어 세 개만 먼저 익힙니다. 학교를 예로 듭니다.

| 용어 | 뜻 | 학교 예 | 나중에 표에서는 |
| --- | --- | --- | --- |
| **엔터티** (Entity, 개체) | 따로 관리할 가치가 있는 대상. 사람 · 물건 · 사건 | 학생, 과목, 교수 | 테이블 |
| **속성** (Attribute) | 엔터티가 가진 특징 | 학생의 이름 · 학년, 과목의 학점 | 열 |
| **관계** (Relationship) | 엔터티끼리의 연결 | 학생이 과목을 **수강한다**, 교수가 과목을 **가르친다** | 외래키, 연결 테이블 |
| **식별자** (Identifier) | 엔터티 하나하나를 구분하는 속성 | 학번, 과목 코드 | 기본키 |

업무 설명 문장에서 찾으면 쉽습니다. **명사**는 엔터티나 속성 후보, **동사**는 관계 후보입니다.

> "**학생**은 학기마다 여러 **과목**을 **수강한다**. 과목마다 **담당 교수**가 한 명 있고, 학생은 과목마다 **성적**을 받는다."

- 엔터티: 학생, 과목, 교수
- 관계: 수강한다(학생 ↔ 과목), 담당한다(교수 ↔ 과목)
- 속성: 성적은 학생에게만 붙는 것도, 과목에만 붙는 것도 아닙니다. **"어떤 학생이 어떤 과목에서 받은"** 성적이라 수강 관계에 붙습니다. 이런 속성 때문에 수강이 나중에 따로 표가 됩니다(다음 레슨의 연결 테이블).

엔터티인지 속성인지 헷갈리면 "이것에 대해 따로 관리할 정보가 더 있나?"를 물어보세요. 학과에 이름만 있다면 학생의 속성이지만, 학과마다 사무실 위치 · 전화번호 · 학과장까지 관리한다면 학과는 독립된 엔터티입니다.

## 개념 모델: 무엇을 관리할까

**개념 모델**은 가장 큰 그림입니다. 어떤 엔터티가 있고 서로 어떻게 연결되는지만 그립니다. 열 이름, 자료형, 어느 DB 제품을 쓸지는 아직 정하지 않습니다. 그래서 개발자가 아닌 사람(선생님, 기획자, 현장 담당자)과 함께 보며 "우리가 관리할 것이 이게 맞나요?"를 확인하는 데 씁니다.

## 논리 모델: 어떤 표 · 열 · 키로 나눌까

**논리 모델**은 개념 모델을 **표의 모양**으로 바꿉니다. 엔터티는 테이블, 속성은 열, 식별자는 기본키, 관계는 외래키가 됩니다. 여기서 중복을 없애도록 표를 나누는 **정규화**도 합니다(다음 코스). 다만 아직 MySQL인지 오라클인지는 신경 쓰지 않습니다.

| 테이블 | 열 | 키 |
| --- | --- | --- |
| 학생 student | 학번, 이름, 학년, 학과 | 학번 = 기본키 |
| 과목 course | 과목 코드, 과목명, 학점, 담당 교수 번호 | 과목 코드 = 기본키, 담당 교수 번호 = 외래키 |
| 교수 professor | 교수 번호, 이름 | 교수 번호 = 기본키 |
| 수강 enroll | 학번, 과목 코드, 성적 | (학번, 과목 코드) = 기본키, 각각 외래키 |

## 물리 모델: 어떤 DB에 어떻게 만들까

**물리 모델**은 논리 모델을 **실제로 쓸 DB 제품**에 맞춰 구체화합니다. 열마다 자료형(정수 · 글자 · 날짜)과 길이를 정하고, 비면 안 되는 열(NOT NULL), 허용할 값의 범위(CHECK), 빠른 검색을 위한 **인덱스**까지 정합니다. 물리 모델의 결과물은 결국 `CREATE TABLE` 문장입니다.

실습 데이터도 누군가 물리 모델을 만들어 둔 것입니다. SQLite는 모든 표의 설계도(CREATE 문)를 `sqlite_master`라는 특별한 표에 보관합니다. 회사 데이터의 사원 표 설계도를 꺼내 봅니다.

```sqlrun
SELECT sql
FROM sqlite_master
WHERE name = 'emp';
```

결과 한 칸에 `emp`를 만든 문장이 그대로 들어 있습니다. 열마다 `INTEGER`(정수) · `TEXT`(글자) 같은 **자료형**이 붙어 있고, `empno`에는 **PRIMARY KEY**(기본키)가 붙어 있습니다. 입사일 `hiredate`가 `TEXT`인 것도 보이는데, SQLite에는 날짜 전용 자료형이 없어서 '2025-01-18' 같은 글자로 저장하기 때문입니다. MySQL이라면 같은 논리 모델을 `DATE` 자료형으로 만듭니다. **논리 모델은 같아도 물리 모델은 DB 제품마다 달라지는** 예입니다.

부서 표의 설계도도 봅니다.

```sqlrun
SELECT name, sql
FROM sqlite_master
WHERE name IN ('dept', 'salgrade');
```

`dept`는 `deptno`가 기본키입니다. `salgrade`에는 기본키가 없습니다. 등급 구간표처럼 행이 몇 개 안 되고 다른 표가 가리키지 않는 표는 기본키 없이 만들기도 하지만, 좋은 습관은 아닙니다. 다음 레슨에서 키를 자세히 봅니다.

> 실무 DB(MySQL)에서는 `SHOW CREATE TABLE emp;`나 `information_schema` 같은 시스템 표로 같은 정보를 봅니다. 이렇게 "데이터를 설명하는 데이터"(표 이름 · 열 · 자료형 · 제약)를 **메타데이터**라고 하고, DB가 메타데이터를 모아 두는 곳을 **시스템 카탈로그(데이터 사전)**라고 부릅니다.

## 세 단계 한눈에 비교

| | 개념 모델 | 논리 모델 | 물리 모델 |
| --- | --- | --- | --- |
| 질문 | 무엇을 관리하나? | 어떤 표 · 열 · 키로 나누나? | 어떤 DB에, 어떤 자료형 · 제약 · 인덱스로 만드나? |
| 그리는 것 | 엔터티와 관계 | 테이블 · 열 · 기본키 · 외래키 | 자료형 · 길이 · NOT NULL · CHECK · 인덱스 |
| DB 제품 | 상관없음 | 상관없음 | 제품에 맞춤 |
| 주로 하는 일 | 업무 담당자와 범위 합의 | 정규화 | 성능 · 저장 공간 고려, 필요하면 반정규화 |
| 결과물 | 개념 ERD | 논리 ERD | `CREATE TABLE` 문 |

전체 순서로 보면 **요구사항 분석 → 개념 → 논리 → 물리 → 구현(DDL 실행)**입니다. 정보처리기사 같은 시험에서는 "개념 · 논리 · 물리"를 줄여 **개논물**로 외우기도 합니다.

## 분석가도 설계를 알아야 할까

표를 직접 설계하는 일은 주로 개발자나 DB 관리자(DBA)가 합니다. 그래도 데이터를 꺼내 쓰는 사람에게 설계 지식은 큰 무기입니다.

- **처음 보는 DB를 빨리 읽습니다.** 표가 왜 이렇게 나뉘었는지 알면 어디를 JOIN해야 할지 바로 보입니다.
- **숫자가 부풀거나 빠지는 이유를 압니다.** 1:N 관계를 모르고 JOIN하면 매출이 두 배로 잡히는 사고([흩어진 표를 키로 잇기](#/l/sq-04-1)의 "행이 불어난다")가 납니다.
- **분석용 표를 직접 만듭니다.** 대시보드용 요약 표, 실험 결과 표처럼 분석가가 직접 테이블을 만드는 일이 생각보다 많습니다.

## 정리

- 데이터 모델링 = 표를 만들기 전에 그리는 설계도. 데이터가 쌓인 뒤에는 구조를 바꾸기 어렵다.
- 엔터티(→ 테이블) · 속성(→ 열) · 관계(→ 외래키, 연결 테이블) · 식별자(→ 기본키).
- 개념 모델은 "무엇을", 논리 모델은 "어떤 표 · 열 · 키로", 물리 모델은 "어떤 DB에 어떻게".
- 물리 모델의 결과물이 `CREATE TABLE`이고, SQLite는 그 문장을 `sqlite_master`에 보관한다.

다음 레슨에서는 설계도를 그리는 그림 언어 **ERD**와, 관계의 모양(1:1 · 1:N · N:M), 키의 종류를 배웁니다.
