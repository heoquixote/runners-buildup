## 여러 행을 숫자 하나로: 집계 함수

"우리 반 평균 점수는?"이라는 질문의 답은 학생 30명의 점수를 **숫자 하나**로 줄인 것입니다. 이렇게 여러 행을 하나의 값으로 요약하는 함수를 **집계 함수**라고 합니다.

| 함수 | 하는 일 | 예 |
| --- | --- | --- |
| `COUNT(*)` | 행 개수 | 사원 수 |
| `SUM(열)` | 합계 | 연봉 총액 |
| `AVG(열)` | 평균 | 평균 연봉 |
| `MIN(열)` · `MAX(열)` | 가장 작은 값 · 큰 값 | 최저 · 최고 연봉 |

```sqlrun
SELECT COUNT(*) AS n, SUM(sal) AS total, AVG(sal) AS avg_sal, MIN(sal) AS min_sal, MAX(sal) AS max_sal
FROM emp;
```

14행이 **1행**으로 줄었습니다. 사원 14명, 연봉 합계 196800, 평균 약 14057입니다. 평균이 높게 나온 이유는 김대표 한 사람의 80000이 평균을 끌어올렸기 때문입니다. (통계 트랙에서 배운 "평균은 극단값에 약하다"가 여기서도 보입니다.)

## COUNT(*)와 COUNT(열)은 다르다

`COUNT(*)`는 행을 모두 세고, `COUNT(열)`은 그 열이 **NULL이 아닌** 행만 셉니다.

```sqlrun
SELECT COUNT(*) AS passengers, COUNT(age) AS age_known, COUNT(deck) AS deck_known FROM titanic;
```

승객은 891명인데 나이가 적힌 승객은 714명, 갑판이 적힌 승객은 203명뿐입니다. `AVG(age)`도 같은 원리로 **NULL을 빼고** 714명의 평균을 냅니다. "평균 나이"를 보고할 때 몇 명으로 낸 평균인지 함께 적어야 하는 이유입니다.

## 0과 1로 된 열의 평균 = 비율

`survived`는 생존 1, 사망 0입니다. 0과 1의 평균을 내면 **1의 비율**, 즉 생존율이 됩니다.

```sqlrun
SELECT AVG(survived) AS survival_rate FROM titanic;
```

0.3838…, 승객 10명 중 약 4명이 살아남았습니다. 891명 중 생존자 수를 891로 나눈 값과 같습니다.


## 타이타닉: 성별 · 객실별 생존율

GROUP BY와 "0/1 평균 = 비율"을 합치면 그룹별 생존율이 바로 나옵니다.

```sqlrun
SELECT sex, COUNT(*) AS n, ROUND(AVG(survived), 3) AS survival_rate
FROM titanic GROUP BY sex;
```

여성 314명 중 74.2%, 남성 577명 중 18.9%가 살아남았습니다. "여성과 어린이 먼저"라는 구조 원칙이 숫자로 보입니다.

**열 여러 개로** 묶으면 두 기준의 조합마다 바구니가 생깁니다. 객실 등급 3개 × 성별 2개 = 6개 바구니입니다.

```sqlrun
SELECT pclass, sex, COUNT(*) AS n, ROUND(AVG(survived), 3) AS survival_rate
FROM titanic GROUP BY pclass, sex ORDER BY pclass, sex;
```

1등실 여성은 96.8%가 살았지만 3등실 남성은 13.5%만 살았습니다. 성별만 볼 때보다 차이가 훨씬 또렷합니다. 기준을 하나 더 쪼개 보는 것이 분석의 기본 동작입니다.

## GROUP BY를 쓰면 SELECT에 쓸 수 있는 것

GROUP BY로 묶은 뒤의 한 줄은 "바구니 하나"입니다. 그래서 SELECT에는 **묶은 열**이나 **집계 함수**만 쓸 수 있습니다. 바구니 안에 사람이 5명인데 `ename_ko`를 쓰면 누구 이름을 보여 줘야 할지 정할 수 없기 때문입니다.

```sqlrun
SELECT deptno, ename_ko, COUNT(*) AS n FROM emp GROUP BY deptno;
```

SQLite는 이 쿼리를 오류 없이 실행하지만, 11번 부서 줄의 이름은 5명 중 **아무나 한 명**입니다. 의미 없는 값이라 결과를 잘못 읽게 만듭니다. MySQL(기본 설정) · PostgreSQL 같은 DB는 이 쿼리를 아예 오류로 막습니다. 규칙대로 쓰는 습관을 들이세요.

## HAVING: 묶은 다음에 거르기

"평균 연봉이 7000 이상인 **직급**만" 보고 싶다면, 조건이 개별 사원이 아니라 **바구니(직급)의 평균**에 걸려 있습니다. 묶은 뒤의 조건은 `HAVING`에 씁니다.

```sqlrun
SELECT joblv, AVG(sal) AS avg_sal FROM emp
GROUP BY joblv HAVING AVG(sal) >= 7000;
```

8개 직급 중 5개가 남았습니다. 과장(평균 7500)은 남고, 대리(평균 5500)는 빠졌습니다.

`WHERE`와 `HAVING`은 둘 다 "거르기"지만 거르는 **때**가 다릅니다.

| | WHERE | HAVING |
| --- | --- | --- |
| 언제 | 묶기 **전** | 묶은 **후** |
| 무엇을 | 행 하나하나 | 바구니(그룹) |
| 집계 함수 | 쓸 수 없음 | 쓸 수 있음 |

둘을 함께 쓸 수도 있습니다. **재직 중인 사원만**(WHERE) 부서별로 묶고, **2명 이상인 부서만**(HAVING) 남깁니다.

```sqlrun
SELECT deptno, COUNT(*) AS n, AVG(sal) AS avg_sal FROM emp
WHERE employed = 1
GROUP BY deptno
HAVING COUNT(*) >= 2;
```

11번 부서가 5명이 아니라 4명입니다. 퇴사한 허태환이 WHERE에서 먼저 빠졌기 때문입니다.

그림의 예시 쿼리를 직접 실행해 봅니다. 승객이 가장 많이 탄 항구는 Southampton(644명)입니다.

```sqlrun
HAVING COUNT(*) > 100
ORDER BY n DESC
LIMIT 1;
```

이 순서를 알면 자주 보는 오류를 설명할 수 있습니다. 평균보다 연봉이 높은 사원을 WHERE로 찾아봅니다.

```sqlrun
-- 오류 예시: 일부러 틀린 쿼리입니다
SELECT ename_ko, sal FROM emp WHERE sal > AVG(sal);
```

`misuse of aggregate function AVG()` 오류가 납니다. WHERE는 행을 하나씩 거르는 단계라서, 아직 묶지도 않았는데 "평균"을 알 수 없기 때문입니다. (이 질문은 평균을 먼저 따로 구해 두는 **서브쿼리**로 풉니다. Day 07에서 배웁니다.)

같은 이유로 SELECT에서 만든 **별칭은 WHERE에서 쓸 수 없는 것이 원칙**입니다. WHERE가 실행될 때 별칭은 아직 만들어지지 않았으니까요. SQLite는 편의상 이를 받아 주지만, MySQL · PostgreSQL · SQL Server에서는 `Unknown column` 오류가 납니다. 반대로 ORDER BY는 SELECT 뒤에 실행되므로 별칭을 마음껏 쓸 수 있습니다(위 쿼리의 `ORDER BY n`).

## 정리

- 집계 함수(`COUNT` · `SUM` · `AVG` · `MIN` · `MAX`)는 여러 행을 값 하나로 줄입니다. `COUNT(열)`과 `AVG(열)`은 NULL을 빼고 계산합니다.
- 0/1 열의 `AVG`는 비율입니다.
- `GROUP BY 열`: 같은 값끼리 묶어 바구니마다 한 줄. SELECT에는 묶은 열과 집계만.
- `WHERE`는 묶기 전 행을, `HAVING`은 묶은 뒤 바구니를 거릅니다.
- 실행 순서 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. WHERE에서 집계 · 별칭을 못 쓰는 이유가 여기에 있습니다.
