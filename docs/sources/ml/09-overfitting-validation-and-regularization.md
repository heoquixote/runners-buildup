오늘은 모델이 왜 실전에 약해지는지 정리합니다.

- 과적합의 감각을 잡습니다.
- 검증 데이터를 왜 따로 둬야 하는지 이해합니다.
- 일반화 성능을 높이는 대표 방법을 익힙니다.
- 불균형 데이터 처리도 `split 이후`에 설계해야 한다는 점을 함께 봅니다.
- 하이퍼파라미터 튜닝도 검증 구조 안에서 해야 한다는 점을 이해합니다.
- AutoML을 써도 누수, 지표 선택, 검증 설계는 여전히 사람이 책임져야 한다는 점을 봅니다.

## 과적합과 과소적합

### 과소적합

모델이 너무 단순해서 학습 데이터조차 잘 설명하지 못하는 상태입니다.

- train 성능 낮음
- validation 성능도 낮음
- 패턴을 충분히 못 배움

### 과적합

학습 데이터에는 너무 잘 맞지만 새로운 데이터에는 약한 상태입니다.

- train 성능 매우 높음
- validation/test 성능 하락
- 잡음과 우연한 패턴까지 외워버림

입문자는 흔히 “점수가 높으니 좋은 모델”이라고 생각하기 쉽지만,  
반드시 `어느 데이터에서 나온 점수인지`를 같이 봐야 합니다.

## 왜 과적합이 생길까

대표 원인은 아래와 같습니다.

- 데이터가 적다
- feature가 너무 많다
- 모델이 지나치게 복잡하다
- 데이터 누수가 있다
- 같은 검증 데이터를 너무 많이 반복해서 본다

즉, 모델 자체 문제만이 아니라 `실험 설계 문제`일 때도 많습니다.

## train / validation / test 다시 보기

- train: 학습
- validation: 모델 선택, threshold 조정, 하이퍼파라미터 튜닝
- test: 최종 1회 성능 확인

이 구분이 필요한 이유는  
모델을 고르는 과정에서 validation에도 점점 맞춰지기 때문입니다.

그래서 마지막 신뢰 점수는 test에서 확인해야 합니다.

즉, `Grid Search`, `Random Search`, `Optuna`처럼  
모델 설정값을 바꾸며 비교하는 작업도 모두 validation 또는 cross validation 안에서 이뤄져야 합니다.

`AutoGluon`, `PyCaret`, `H2O AutoML`, `AutoSklearn` 같은 AutoML 도구도 마찬가지입니다.  
자동으로 모델 후보를 돌려준다고 해도 `split`, `metric`, `target leakage 점검`은 먼저 설계되어 있어야 합니다.

## 교차검증은 왜 쓰는가

데이터가 많지 않으면 한 번의 split 결과가 우연에 크게 좌우될 수 있습니다.  
이때 `K-Fold Cross Validation`을 사용하면 여러 분할에서 평균 성능을 볼 수 있습니다.

간단히 말하면:

1. 데이터를 여러 조각으로 나눕니다.
2. 번갈아 가며 일부를 검증용으로 씁니다.
3. 점수 평균을 봅니다.

이 방식은 점수의 `안정성`을 확인하는 데 도움이 됩니다.

## 정규화는 무엇을 하는가

정규화(regularization)는 모델이 너무 복잡해지지 않도록 벌점을 주는 방식입니다.

대표적으로:

- L1 regularization: 불필요한 계수를 0으로 만들기 쉬움
- L2 regularization: 큰 계수를 완만하게 줄임

직관적으로는 아래처럼 이해하시면 됩니다.

- 데이터를 설명하되
- 계수를 너무 과하게 키우지 말자

즉, `훈련 데이터에 지나치게 집착하는 것`을 막는 안전장치입니다.

## 데이터 누수는 과적합처럼 보이기도 합니다

누수가 있으면 validation/test 점수도 비정상적으로 높게 나올 수 있습니다.  
그래서 단순한 과적합보다 더 위험합니다.

증상:

- 점수가 지나치게 좋다
- 실제 배포 후 성능이 급격히 하락한다
- 미래 정보가 feature에 섞여 있다

즉, “검증 점수가 높다”와 “진짜로 일반화된다”는 다른 이야기입니다.

## 불균형 데이터도 검증 설계를 흔들 수 있습니다

양성 클래스가 매우 적은 분류 문제에서는  
학습 데이터를 어떻게 구성하느냐에 따라 점수가 크게 달라질 수 있습니다.

예:

- `class_weight` 적용
- random oversampling
- undersampling
- `SMOTE`

이런 방법들은 유용할 수 있지만,  
`train/test split 전에 전체 데이터에 적용하면` 검증 점수가 비정상적으로 좋아질 수 있습니다.

즉, 불균형 데이터 처리는 성능 향상 기법이면서 동시에  
`누수와 검증 왜곡을 만들 수 있는 실험 설계 요소`이기도 합니다.

## 작은 코드 예시

```python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score

model = LogisticRegression(max_iter=1000, C=1.0)
scores = cross_val_score(model, X, y, cv=5, scoring="f1")

print(scores)
print(scores.mean())
```

여기서 중요한 해석은:

- 각 fold 점수가 크게 흔들리는가
- 평균 점수가 baseline 대비 나은가
- 특정 split에만 강한 모델은 아닌가

## 실무에서 언제 문제가 되는가

### 1. feature 수는 많은데 표본 수는 적은 경우

분석 프로젝트에서 자주 나옵니다.  
표본은 적은데 파생 컬럼을 계속 늘리면 과적합 위험이 커집니다.

### 2. leaderboard 점수만 따라가며 반복 튜닝하는 경우

검증 리더보드에 과적합되면 실제 배포 성능이 떨어질 수 있습니다.

### 3. 시간축 문제를 일반 random split로 처리하는 경우

미래 예측 문제라면 과거 데이터로 학습하고 미래 데이터로 검증해야 합니다.  
그렇지 않으면 현실보다 낙관적인 점수가 나올 수 있습니다.

## 대안은 무엇인가

과적합이 의심되면 아래를 점검합니다.

- 더 단순한 모델 사용
- feature 수 줄이기
- 규칙 기반 baseline 비교
- 더 많은 데이터 확보
- 교차검증
- 정규화 강도 조정
- 하이퍼파라미터 튜닝 범위 재설계
- 조기 종료(특히 boosting 계열)
- 불균형 데이터라면 `class_weight`, 리샘플링, `SMOTE` 적용 위치 점검
- 반복 실험 속도가 너무 느리면 `AutoML`로 강한 baseline을 먼저 만들고, 그다음 수동 튜닝 범위를 줄이기

즉, 해결책은 “더 강한 모델”이 아니라 “더 신뢰할 수 있는 학습 설계”일 때가 많습니다.

## 처음엔 이렇게 보면 됩니다

- train 높고 validation 낮다 -> 과적합 의심
- train도 validation도 낮다 -> 과소적합 의심
- validation을 많이 보면 결국 validation에도 익숙해진다
- test는 마지막에만 본다
- 누수는 과적합보다 더 위험할 수 있다
