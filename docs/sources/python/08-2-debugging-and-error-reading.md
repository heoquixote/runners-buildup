## 학습 목표

- 에러 메시지를 읽고 원인을 단계적으로 좁힐 수 있습니다.
- 디버깅을 감이 아니라 절차로 접근할 수 있습니다.
- 재현, 관찰, 분리, 검증의 흐름을 이해할 수 있습니다.

## 사용 라이브러리

- 표준 라이브러리: `pdb`
- 외부 라이브러리: 없음

## 왜 디버깅이 중요한가

좋은 개발자는 에러를 전혀 만들지 않는 사람이 아니라, 에러를 `빠르게 읽고`, `원인을 좁히고`, `정확히 수정하는 사람`입니다.

실무에서는 새로운 기능을 짜는 시간만큼 디버깅 시간이 중요합니다.

- 파일이 안 읽힌다
- 값이 이상하게 나온다
- 특정 조건에서만 에러가 난다
- 분명 코드는 돌아가는데 결과가 틀리다

이런 문제를 해결하는 능력이 곧 디버깅 능력입니다.

## 에러 메시지는 무엇을 알려주는가

Python 에러 메시지에는 보통 다음 정보가 들어 있습니다.

- 어떤 종류의 에러인지
- 어느 파일, 어느 줄에서 났는지
- 어떤 호출 흐름을 따라왔는지

예:

```python
numbers = [1, 2, 3]
print(numbers[5])
```

이 코드는 `IndexError`를 발생시킵니다.

핵심은 `에러 이름`과 `마지막 줄`을 먼저 읽는 것입니다.

## Traceback 읽는 법

보통 Traceback은 `아래에서 위로` 읽는 것이 빠릅니다.

1. 마지막 줄: 어떤 예외인가
2. 그 위의 줄: 어느 파일, 어느 줄인가
3. 위쪽 흐름: 어떤 함수 호출을 통해 왔는가

즉, 가장 아래가 현재 문제의 핵심인 경우가 많습니다.

## 자주 만나는 에러 유형

### `SyntaxError`

문법이 잘못되었습니다.

```python
if True
    print("hello")
```

### `NameError`

정의되지 않은 이름을 사용했습니다.

```python
print(user_name)
```

### `TypeError`

타입이 맞지 않습니다.

```python
print("10" + 5)
```

### `ValueError`

타입은 맞지만 값 형식이 잘못되었습니다.

```python
int("abc")
```

### `KeyError`

딕셔너리에 없는 키를 찾았습니다.

### `IndexError`

리스트 범위를 벗어난 인덱스입니다.

### `AttributeError`

해당 객체에 없는 속성이나 메서드를 호출했습니다.

## 디버깅의 기본 절차

### 1. 재현

같은 문제가 다시 발생하는지 확인합니다.

- 언제 발생하는가
- 어떤 입력에서 발생하는가
- 항상 발생하는가, 특정 상황에서만 발생하는가

재현이 안 되면 수정도 불안정합니다.

### 2. 관찰

문제가 나는 지점 직전의 값을 확인합니다.

```python
print(type(value))
print(value)
```

초보자에게 `print 디버깅`은 여전히 강력합니다.

### 3. 분리

문제가 생기는 코드를 작은 단위로 나눕니다.

예:

- 파일 읽기 문제인가
- 형변환 문제인가
- 반복문 로직 문제인가

### 4. 가설 세우기

`아마 이 값의 타입이 문자열이라서 문제가 났다`처럼 원인을 추정합니다.

### 5. 검증

가설이 맞는지 코드와 입력을 바꿔 확인합니다.

## `print()` 디버깅

가장 단순하지만 효과적인 방법입니다.

```python
price = "1000"
tax = 100

print(type(price), price)
print(type(tax), tax)
print(price + str(tax))
```

값과 타입을 함께 출력하면 문제를 빨리 찾을 수 있습니다.

## `breakpoint()`와 `pdb`

조금 더 체계적으로 멈춰서 보고 싶다면 `breakpoint()`를 사용할 수 있습니다.

```python
def calculate_total(price, quantity):
    breakpoint()
    return price * quantity

calculate_total(1000, 3)
```

이렇게 하면 실행이 멈추고 현재 변수 상태를 살펴볼 수 있습니다.

입문 단계에서는 `print()`만으로도 충분하지만, 코드가 길어지면 `breakpoint()`가 큰 도움이 됩니다.

## 논리 버그와 런타임 에러는 다르다

에러 메시지가 뜨는 문제는 비교적 찾기 쉽습니다. 더 어려운 것은 `코드는 돌아가는데 결과가 틀린 경우`입니다.

예:

```python
prices = [1000, 2000, 3000]
total = 0

for price in prices:
    total = price

print(total)
```

이 코드는 오류 없이 실행되지만 결과는 `6000`이 아니라 `3000`입니다.

이런 문제는:

- 변수 변화 추적
- 중간 출력
- 작은 예제로 검증

이 중요합니다.

## 디버깅할 때 좋은 질문

- 입력값은 내가 생각한 타입이 맞는가
- 반복문이 몇 번 도는가
- 조건문이 어느 분기로 들어가는가
- 함수가 무엇을 반환하는가
- 원본 데이터가 중간에 바뀌고 있지는 않은가

이 질문을 습관처럼 던지면 디버깅 속도가 빨라집니다.

## 실무에서 자주 하는 실수

### 1. 에러 메시지를 끝까지 읽지 않음

한 줄만 보고 감으로 고치면 문제를 더 키울 수 있습니다.

### 2. 여러 부분을 동시에 수정

무엇 때문에 해결됐는지 알 수 없게 됩니다.

### 3. 재현 없이 고치기

운 좋게 사라진 것처럼 보여도 다른 곳에서 다시 터질 수 있습니다.

### 4. 결과만 보고 중간 상태를 보지 않기

중간 변수 상태를 보면 원인이 빨리 드러나는 경우가 많습니다.

## 추천 디버깅 루틴

1. 에러 메시지를 끝까지 읽는다
2. 마지막 줄의 예외 종류를 확인한다
3. 문제 줄 직전 변수 값을 출력한다
4. 코드를 작은 예제로 축소한다
5. 한 번에 한 가지씩만 수정한다
6. 수정 후 다시 재현해 본다

## 추천 예제

```python
raw_score = "85"

print("type:", type(raw_score))
print("value:", raw_score)

score = int(raw_score)

if score >= 80:
    print("우수")
else:
    print("보통")
```

이렇게 작은 단위부터 확인하는 습관이 실제로는 가장 강력합니다.

## 정리

이번 페이지의 핵심은 다음입니다.

- 디버깅은 감이 아니라 절차입니다.
- 에러 메시지와 Traceback을 읽는 습관이 중요합니다.
- 재현, 관찰, 분리, 검증의 흐름으로 접근하면 훨씬 빠르게 원인을 찾을 수 있습니다.

디버깅 능력은 문법 암기보다 오래 갑니다. 이 능력이 쌓이면 새로운 라이브러리나 큰 프로젝트를 만나도 훨씬 덜 흔들리게 됩니다.
