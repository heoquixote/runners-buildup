# SQL 트랙 레슨 기획안

작성 기준은 [README.md](README.md). 기호: `S` 설명, `F` 그림, `C` 실행 셀, `T` 직접 해보기, `R` 결과 해석.

원본은 진성 님의 SQL 기초 원고(`docs/sources/sql/`, 위키독스 러너스 스쿨 교재)입니다. 원고는 실무자·BI 독자 기준이고 MySQL + DBeaver로 실습합니다. 레슨에서는 전제 개념을 보태고 고등학생~대학 초년생 눈높이로 풀어 쓰며, 실습은 설치 없이 브라우저 안에서 합니다.

## 실행 방식

- **확인한 것**: 이 트랙은 지금까지 `ready: false`(준비 중)였고, 사이트에 SQL 실행 기능이 없었습니다. 코딩 셀은 모두 Pyodide(브라우저 파이썬) Worker로 돌아갑니다.
- **고른 방법**: Pyodide에 들어 있는 `sqlite3` 모듈(SQLite 3.39)로 SQL을 실행합니다. 새 엔진(sql.js 등)을 따로 받지 않고 기존 Worker를 그대로 쓰므로, 로딩 · 시간 제한 · 데이터 파일 내려받기가 파이썬 셀과 똑같이 동작합니다. 로컬 검증(`scripts/verify.mjs`)도 같은 코드를 CPython의 sqlite3로 돌립니다.
- 레슨 md에서 ` ```sqlrun ` 펜스가 SQL 실행 셀입니다. 실행할 때마다 메모리에 새 DB를 만들고, 쿼리에 나온 테이블의 데이터만 넣습니다. 그래서 학생이 `DELETE`를 해도 다음 실행에는 원래대로 돌아옵니다.
- 결과는 HTML 표로 보여 줍니다 (100행까지, 전체 행 수 표시). 자주 나는 오류(`no such column`, 집계 함수를 WHERE에, `CONCAT` 없음 등)에는 쉬운 말 안내를 붙입니다.
- 체크 퀴즈의 코드 작성 문항은 `lang: "sql"`로 씁니다. 학생 쿼리 결과 표와 예시 답안 결과 표를 값으로 비교합니다(열 이름은 보지 않고, 예시 답안 바깥에 ORDER BY가 있을 때만 순서까지 비교).
- **SQLite와 MySQL의 차이**: 원고는 MySQL 기준입니다. 레슨은 표준에 가까운 문법을 쓰고, 다른 곳만 "MySQL에서는" 박스로 짚습니다. 주요 차이: 문자열 잇기 `||`(MySQL `CONCAT`), `SUBSTR`(MySQL `LEFT/RIGHT/SUBSTRING`), `IIF`/`CASE`(MySQL `IF`), `strftime`·`date()`(MySQL `DATE_FORMAT`·`DATE_ADD`), 정수끼리 나누면 몫만 남음(MySQL은 소수).

## sq-00 페이지 1 (sq-00-0) SQL은 무엇이고, 왜 SQL인가

파이썬 트랙의 첫 페이지(pb-00-1 "파이썬은 무엇이고, 왜 파이썬인가")와 같은 자리 · 같은 구성의 소개 페이지. 진성 님 요청(2026-11-05): "파이썬 참고해서 SQL에도 1페이지에 소개 하나 넣자".

- **목표**: SQL과 데이터베이스가 무엇인지, 어디에 쓰이는지, 엑셀 · 파이썬과 무엇이 다른지 설명하고, 이 사이트에서 SQL이 어떻게 실행되는지 안다.
- **전제 개념**: 없음.
- **알아야 할 개념**
  1. 데이터베이스(DB)와 DBMS: 데이터를 오래 · 안전하게 · 여럿이 함께 쓰려고 만든 창고와 창고 관리 프로그램
  2. SQL = DBMS에게 "무엇을" 원하는지 적는 언어 (선언형). "어떻게" 찾을지는 DB가 정한다 → 식당 주문서 비유
  3. SQL이 쓰이는 곳: 데이터 분석 · BI 대시보드(Tableau 등) · 서비스 백엔드 · 마케팅 · 생산 현장. 직무 이름보다 "DB에서 꺼내는 일"이 공통
  4. 역사: 1970 Codd 관계형 모델 → 1974 IBM SEQUEL → 1979 Oracle 첫 상용 → 1986 ANSI 표준 → 1995 MySQL · 1996 PostgreSQL · 2000 SQLite → 2010년대 클라우드(BigQuery · Snowflake). 50년 넘게 표준
  5. DBMS 종류와 방언: Oracle · MySQL · PostgreSQL · SQL Server · SQLite · BigQuery. 핵심 문법은 같고 함수 이름 등이 조금씩 다르다
  6. 엑셀 · 파이썬과 비교: 데이터 크기, 여러 사람이 동시에, 작업 기록, 잘하는 일. 실무에서는 함께 쓴다
  7. 이 사이트에서 SQL이 실행되는 방식: 브라우저 안 SQLite, 셀마다 새 DB + 실습 데이터, 서버로 보내지 않음, 설치 불필요. 내 PC에서 하려면 DB Browser for SQLite · DBeaver · MySQL Workbench
- **배치**: 로고 상자(자체 DB 아이콘) → S(SQL이란) → C(`SELECT '안녕하세요, SQL!' AS greeting;` 한 줄 맛보기) → S(DB · DBMS 비유: 도서관과 사서) → **F1**(주문서 비유: 손님(SQL 문장) → DBMS(주방) → 결과 표, "무엇을"만 적는다) → S(선언형 설명) → **F2**(SQL 허브 그림: DB 가운데, 분석 · 대시보드 · 서비스 · 리포트로 뻗음) → S(쓰이는 곳 목록) → **F3**(연표) → 표(연도 · 사건 · 의미) → 표(DBMS 종류) → S(방언) → 표(엑셀 · SQL · 파이썬 비교) → **F4**(실무 흐름: DB → SQL로 꺼내기 → 엑셀 · 파이썬 · BI) → S(이 사이트의 실행 방식) → **F5**(셀 → 브라우저 안 SQLite(새 DB + 실습 데이터) → 결과 표, 서버로 안 감) → S(내 PC에서 하려면) → 다음 페이지 안내
- **퀴즈 vs 코드**: 퀴즈 없음(소개 코스). 실행 셀은 맛보기 1개(데이터 없이 도는 한 줄)만. 실제 표 조회는 다음 페이지에서.
- **그림**: F1 주문서 비유, F2 SQL 허브, F3 연표, F4 실무 데이터 흐름, F5 이 사이트의 실행 구조. 모두 인라인 SVG, 파이썬 소개와 같은 클래스(`box` · `box-accent` · `hub` · `axis-a/b` 등).
- **원본 원고**: 01-1-why-learn-sql(왜 SQL을 배우나, 데이터 리터러시), 01-database-and-table-understanding(DB · DBMS). 역사 · DBMS 종류는 원고에 없어 새로 씀.

## sq-00 페이지 2 (sq-00-1) 데이터베이스 구조와 첫 쿼리

- **목표**: 데이터베이스 · 테이블 · 행 · 열 · 키를 구분하고, 이 사이트에서 첫 쿼리를 실행할 수 있다.
- **전제 개념**: 없음. 엑셀을 본 적이 있다는 정도만 가정.
- **알아야 할 개념**
  1. 데이터가 사는 곳: 회사 데이터는 엑셀 파일이 아니라 데이터베이스(DB)에 있다
  2. SQL = DB에 묻는 질문 문장. 일상 질문을 "어느 표 / 어떤 조건 / 무엇을 기준으로 / 무엇을 셀까"로 바꾸기 (데이터 리터러시)
  3. 구조: 서버 > 데이터베이스(=스키마) > 테이블 > 열 · 행
  4. 키: 행을 하나로 짚는 번호(기본키), 다른 표를 가리키는 번호(외래키)
  5. 이 사이트의 실행 방식(브라우저 안 SQLite, 매번 새 DB)과 실무 도구(MySQL + DBeaver)
  6. 실습 데이터 세 가지 소개
- **배치**: S(질문을 SQL로 바꾸기 표) → **F1**(서버 > DB > 테이블 > 행 · 열 상자 그림) → S(용어 표: 테이블 = 엑셀 시트) → C(`SELECT * FROM dept;`) → R(5행 3열 짚기) → S(행 · 열) → C(`SELECT * FROM emp;`) → R → S(키) → **F2**(emp.deptno → dept.deptno, emp.mgr → emp.empno 화살표) → C(salgrade) → S(셀 사용법: ▶, Ctrl+Enter, 원래대로. 실행 구조는 페이지 1에서) → S(회사 · 쇼핑몰 데이터 소개) → C(`SELECT * FROM orders LIMIT 5;`) → S(다음 레슨 안내)
- **퀴즈 vs 코드**: **퀴즈 없음**(소개 코스, '다 읽었어요'로 완료). 용어를 외우게 하는 퀴즈보다 셀을 직접 눌러 보는 것이 이 단계의 목표.
- **그림**: F1 데이터베이스 구조(서버 > DB > 테이블, 테이블 안 행 · 열 강조), F2 세 테이블 관계도(ERD 간이판)
- **영상 위치**: 없음
- **원본 원고**: 01-1-why-learn-sql(데이터 리터러시, 질문 → 테이블 · 조건 · 기준 · 집계 · 기간), 01-2-database-basic-structure(인스턴스 · DB · 스키마 · 테이블 · 컬럼 · 행), 02-2-practice-data-introduction(실습 테이블 정의서). DBeaver 설치(02-1)는 빼고 "실무에서는" 한 단락으로만.

## sq-01 필요한 열만, 필요한 행만 (SELECT · WHERE)

- **목표**: 원하는 열만 고르고(SELECT), 조건에 맞는 행만 남길(WHERE) 수 있다.
- **전제 개념**: sq-00의 테이블 · 행 · 열
- **알아야 할 개념**
  1. SELECT = 세로로 열 고르기, FROM = 어느 표에서 (`*`는 모든 열)
  2. AS 별칭: 결과 화면에서만 바뀌는 이름
  3. 계산 열: `sal + comm`
  4. DISTINCT: 중복 빼고 종류만
  5. WHERE = 가로로 행 거르기. 비교 연산자, 문자는 작은따옴표
  6. AND · OR, 괄호로 묶기
  7. IN · BETWEEN (양 끝 포함)
  8. LIKE: `%`(아무 글자 여러 개) `_`(한 글자)
  9. NULL: 0도 빈칸도 아닌 "모름". `= NULL`은 안 되고 `IS NULL`
- **배치**: S(엑셀에서 열 숨기기 · 필터 비유) → **F1**(SELECT는 세로, WHERE는 가로로 자르는 그림) → C(전체) → C(열 3개) → S(별칭) → C(AS) → S(계산 열) → C(sal + comm) → S(DISTINCT) → C → R(직급 8종) → S(WHERE) → C(sal >= 10000) → C(문자 조건) → S(AND · OR) → C(AND) → **T**(괄호 빼면 결과가 달라지는지) → S(IN · BETWEEN) → C → C → S(LIKE) → C(`김%`) → C(`_정%`) → S(NULL) → C(`= NULL` 0행) → C(`IS NULL`) → R → S(쇼핑몰: 행이 많을 때) → C(events 비회원 NULL 488건) → C(전자 30만 원 이상) → S(정리 표)
- **퀴즈 vs 코드**: **퀴즈 3문항** (SQL 작성 2 + ox 1). 조건을 직접 써 보는 것이 핵심이라 작성형 위주. NULL 비교는 오개념이 흔해서 ox로.
  - write: 11번 부서 과장 · 대리의 이름 · 직급 (원고 3-3 문제 3) / write: 전자 분류 중 30만 원 이상 주문(8건) / ox: `WHERE comm = NULL`로 NULL인 행을 찾을 수 있다(X)
- **그림**: F1 열 고르기 · 행 거르기 표 그림

## sq-02 줄 세우고, 자르고, 계산하기 (ORDER BY · LIMIT · 숫자 함수)

## sq-04 흩어진 표를 키로 잇기 (JOIN · UNION)

- **목표**: 공통 키로 두 표를 잇고, INNER JOIN과 LEFT JOIN의 결과 차이를 설명할 수 있다.
- **전제 개념**: sq-00 키, sq-03 GROUP BY, sq-06 NULL
- **알아야 할 개념**
  1. 왜 표를 나눠 두나 (부서 이름이 바뀌면 14곳 대신 1곳만 고친다)
  2. JOIN ... ON 키 = 키, 테이블 별칭
  3. INNER JOIN: 양쪽에 짝이 있는 행만
  4. LEFT JOIN: 왼쪽 표는 모두, 짝이 없으면 NULL
  5. "한 번도 주문 안 한 고객" = LEFT JOIN + IS NULL
  6. LEFT JOIN 뒤 COUNT(*) vs COUNT(오른쪽 열)
  7. 키가 중복되면 행이 불어난다
  8. SELF JOIN (사원 → 상사 이름), 범위 조인(급여 등급)
  9. UNION · UNION ALL: 위아래로 붙이기 (JOIN은 옆으로)

- **퀴즈 vs 코드**: **퀴즈 3문항**. JOIN 문법은 작성형, 결과 행 수는 판단형(실무 사고의 대부분이 행 수 착각).
  - write: 지역(location)별 평균 급여 (원고 7-1 문제 3) / choice: 고객 256명 · 주문 372건을 users LEFT JOIN orders 하면 결과는 최소 몇 행? / ox: UNION은 중복 행을 지우고 UNION ALL은 지우지 않는다(O)
- **그림**: F1 키로 줄 잇기, F2 INNER와 LEFT 결과 나란히
- **영상 위치**: dl-m04 JOIN 종류: INNER vs LEFT 그림 바로 뒤

## sq-05 쿼리 안의 쿼리, 이름 붙인 중간 결과 (서브쿼리 · CTE)

## sq-07 행을 지우지 않고 순위 · 누적 구하기 (윈도우 함수)

- **목표**: 순위 · 그룹 안 순번 · 누적합 · 이전 행 값을 구하고, 그룹별 1등만 뽑을 수 있다.
- **전제 개념**: sq-03 GROUP BY, sq-05 CTE
- **알아야 할 개념**
  1. GROUP BY는 행을 접고, 윈도우는 행을 그대로 두고 옆에 값을 붙인다
  2. `함수() OVER (ORDER BY …)`
  3. ROW_NUMBER · RANK · DENSE_RANK (동점 처리 차이)
  4. PARTITION BY: 그룹 안에서 따로
  5. 그룹별 1등 = CTE + ROW_NUMBER = 1
  6. 누적합 SUM() OVER (ORDER BY)
  7. LAG · LEAD: 이전 · 다음 행 (전월 대비)
  8. 이동평균: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
- **배치**: S(성적표 등수 비유) → **F1**(GROUP BY vs 윈도우: 접기 vs 옆에 붙이기) → C(부서 평균을 모든 행 옆에) → R → S(순위) → C(세 가지 순위 함수) → R(6000 동점 짚기) → S(PARTITION BY) → C(직급 안 순위) → S(그룹별 1등) → C(CTE + ROW_NUMBER) → ::video dl-m20 → S(누적합) → C(월별 매출 → 누적) → R → S(LAG) → C(전월 대비 증감) → S(이동평균) → C(3개월 이동평균) → **T**(2 PRECEDING을 1로) → S(정리 표)
- **퀴즈 vs 코드**: **퀴즈 2문항**. 동점 처리는 판단형, 그룹별 1등은 실무 빈출이라 작성형.
  - choice: 급여 80, 60, 60, 50에 RANK를 붙이면 / write: 부서별 급여 1등 사원의 부서 번호 · 이름 · 급여
- **그림**: F1 GROUP BY와 윈도우 함수 비교
- **영상 위치**: dl-m20 윈도우 함수: PARTITION BY 설명 뒤, 누적합 직전
- **원본 원고**: 06-window-functions(개념, 함수 표, 문제 1~4), 08-3-inline-view 문제 2(부서별 1등)
- **원고 반영**: 원고 문제 1(ROW_NUMBER) · 2(직급별 DENSE_RANK) · 4(LAG/LEAD)를 실행 셀로. 원고 문제 3(누적 평균)은 프레임 개념이 더 잘 보이는 쇼핑몰 월별 매출 누적합으로 바꿈. 이동평균 프레임은 새로 추가.

## sq-08 매출 · 퍼널 · 리텐션 쿼리 (실무 분석)

- **목표**: 월별 핵심 지표, 단계별 전환율(퍼널), 가입 월별 재구매율(리텐션 코호트)을 SQL로 만들 수 있다.
- **전제 개념**: sq-03 집계, sq-04 JOIN, sq-05 CTE, sq-06 날짜, sq-07 LAG
- **알아야 할 개념**
  1. 지표를 정의부터: 매출 · 주문 수 · 구매자 수 · 객단가
  2. 월별 KPI 표 (+ 전월 대비)
  3. 퍼널: 단계별 세션 수와 전환율, 분모가 무엇인지
  4. 재구매율: 2번 이상 산 고객 비율
  5. 코호트: 같은 달 가입한 고객 묶음
  6. 리텐션: 가입 n개월 뒤에도 산 고객 비율
  7. 채널별로 나눠 보기 (추천 고객의 리텐션)
- **배치**: S(데이터 분석가의 하루) → S(가상 쇼핑몰 데이터 소개) → C(테이블 미리보기) → S(지표 정의 표) → C(월별 KPI) → R → C(전월 대비 LAG) → S(퍼널) → **F1**(퍼널 막대: visit 620 → purchase 48) → C(단계별 세션 수) → C(전환율) → R(가장 많이 새는 단계) → S(재구매율) → C → S(코호트 · 리텐션) → **F2**(코호트 표 읽는 법: 가로 = 경과 월, 세로 = 가입 월) → C(첫 구매 월 · 경과 월 CTE) → C(코호트 표) → R → C(채널별 리텐션) → R → S(정리: 분석 쿼리 작성 순서)
- **퀴즈 vs 코드**: **퀴즈 2문항**. 실무 쿼리는 길어서 작성형보다 **해석과 정의** 판단이 핵심.
  - choice: 장바구니 → 구매 전환율의 분모 / ox: 7월에 가입한 코호트가 없으면 7월 매출 감소는 신규 유입이 없어서일 수 있다(O)
- **그림**: F1 퍼널 막대, F2 코호트 표 읽는 법
- **원본 원고**: 01-1-why-learn-sql(비즈니스 질문 → 데이터 구조)만. 리텐션 · 퍼널 · 코호트는 원고에 없어 새로 씀.

**실행 방식 변경**: SQL 셀의 SQLite 연결을 자동 커밋 모드(`isolation_level=None`)로 바꿨습니다. 파이썬 sqlite3의 기본값은 INSERT 앞에 몰래 트랜잭션을 열어서, 학생이 쓴 `BEGIN`이 "cannot start a transaction within a transaction" 오류를 냈습니다. 자동 커밋은 DBeaver · MySQL Workbench의 기본값과 같습니다. 조회 셀에는 영향이 없습니다. 제약조건 위반 오류(NOT NULL · UNIQUE · FOREIGN KEY · CHECK)와 "이미 있는 테이블" 오류에 쉬운 말 안내를 추가했습니다.

**SQLite와 MySQL 차이(설계 구역)**: ① 외래키 검사는 `PRAGMA foreign_keys = ON;`을 켜야 동작(MySQL InnoDB는 기본). ② 자료형이 느슨함(INTEGER 열에 글자가 들어감, 타입 친화성). ③ 날짜 전용 자료형이 없어 TEXT로 저장. ④ TRUNCATE 없음(`DELETE FROM 표`). ⑤ `EXPLAIN QUERY PLAN`(MySQL은 `EXPLAIN`). 각 레슨에서 "MySQL에서는" 박스로 짚습니다.

**데이터**: 설계 레슨은 학생이 셀 안에서 직접 `CREATE TABLE`로 작은 표(수강 신청 · 동아리 · 계좌)를 만들고 씁니다. 셀마다 새 DB라 표 만들기 → 넣기 → 조회를 한 셀에 둡니다. 실습 데이터 테이블 이름(emp · dept · salgrade · users · orders · events)은 새 표 이름으로 쓰지 않습니다(쓰면 실습 데이터가 먼저 로드되어 "이미 있음" 오류). 인덱스 · 반정규화 · DML은 행이 많은 쇼핑몰 · 회사 데이터를 씁니다.

## sq-09-1 설계도부터 그리기: 개념 · 논리 · 물리 모델

- **목표**: 데이터 모델링이 왜 필요한지, 개념 · 논리 · 물리 모델이 각각 무엇을 정하는지 설명할 수 있다.
- **전제 개념**: 테이블 · 행 · 열 · 키(데이터베이스 구조와 첫 쿼리), JOIN으로 표 잇기
- **알아야 할 개념**
  1. 모델링 = 표를 만들기 전에 그리는 설계도. 잘못 설계하면 나중에 고치기 어렵다
  2. 엔터티(관리할 대상: 학생 · 과목) · 속성(특징: 이름 · 학년) · 관계(학생이 과목을 수강한다)
  3. 업무 문장에서 명사 → 엔터티 · 속성, 동사 → 관계 찾기
  4. 개념 모델: 무엇을 관리하나 (엔터티와 관계만, DB 종류 무관)
  5. 논리 모델: 어떤 표 · 열 · 키로 나누나 (정규화, 아직 DB 제품 무관)
  6. 물리 모델: 어떤 DB에 어떤 자료형 · 제약 · 인덱스로 만드나 (DB 제품에 맞춤) → 결과물이 CREATE TABLE
  7. 설계 전체 순서: 요구사항 → 개념 → 논리 → 물리 → 구현
- **배치**: S(시작하기 전에) → S(집 짓기 비유) → **F1**(건축 3단계 ↔ 모델링 3단계) → S(엔터티 · 속성 · 관계) → 표(학교 예) → S(문장에서 찾기) → S(개념 모델) → **F2**(학생 · 과목 · 수강 개념 그림) → S(논리 모델) → 표 → S(물리 모델) → C(회사 DB의 실제 설계도: sqlite_master에서 emp DDL 보기) → R(자료형 · PRIMARY KEY 짚기) → C(dept DDL) → S(세 단계 비교 표) → S(실무에서 누가 하나, 분석가가 알아야 하는 이유) → S(정리)
- **퀴즈 vs 코드**: 이 레슨은 개념 정리, 퀴즈는 코스 끝(sq-09-2)에서 3문항으로.
- **그림**: F1 건축과 모델링 3단계, F2 개념 → 논리 → 물리로 같은 대상이 구체화되는 모습
- **원본**: 03-2 §2 단계 표 · 설계 전체 단계, §4 엔터티 · 속성 · 관계, §9 비유

## sq-09-2 ERD 읽기: 관계 · 카디널리티 · 키

- **목표**: ERD를 읽고 1:1 · 1:N · N:M을 구분하며, N:M을 연결 테이블로 바꾸고, 키 종류를 구분할 수 있다.
- **알아야 할 개념**
  1. ERD = 표와 관계를 그린 그림. Chen 표기(사각형 · 타원 · 마름모)와 실무 까마귀발 표기
  2. 카디널리티: 1:1 · 1:N · N:M, "한 명의 ~는 몇 개의 ~와?" 두 방향 질문
  3. 1:N에서 외래키는 N쪽에 둔다
  4. N:M은 연결 테이블로 1:N 두 개로 푼다
  5. 키 종류: 슈퍼키 → 후보키(유일 + 최소) → 기본키 / 대체키, 외래키
  6. 복합키, 자연키 vs 대리키(실무는 대리키 + UNIQUE)
- **배치**: S(시작하기 전에) → S(ERD) → **F1**(Chen vs 까마귀발 표기) → **F2**(까마귀발 기호 읽는 법) → S(카디널리티 두 방향 질문) → C(dept 1 : emp N 확인: 부서별 인원) → C(users 1 : orders N 확인) → S(외래키는 N쪽) → S(N:M) → **F3**(학생 N:M 과목 → 수강 연결 테이블) → C(연결 테이블 만들고 JOIN) → R → S(키 종류) → **F4**(키 포함 관계 그림) → 표 → S(복합키 · 대리키) → S(회사 · 쇼핑몰 ERD 다시 읽기) → S(정리)
- **퀴즈 vs 코드**: 퀴즈 3 (choice 외래키 위치 / choice N:M 해소 / ox 후보키 최소성). 관계 판단은 표를 만드는 문제보다 짧은 판단형이 효과적.
- **그림**: F1 표기법 비교, F2 까마귀발 기호, F3 연결 테이블, F4 키 포함 관계

## sq-10-1 한 사실은 한 곳에: 이상 현상과 정규화

- **목표**: 중복이 만드는 세 가지 이상 현상을 직접 보고, 1NF · 2NF · 3NF로 표를 나눌 수 있다.
- **알아야 할 개념**
  1. 중복 표의 문제 = 이상 현상(삽입 · 갱신 · 삭제)
  2. 함수 종속: A를 알면 B가 하나로 정해진다 (학번 → 이름)
  3. 1NF: 한 칸에 값 하나
  4. 2NF: 복합키의 일부에만 기대는 열을 떼어 낸다 (부분 종속)
  5. 3NF: 키가 아닌 열에 기대는 열을 떼어 낸다 (이행 종속)
  6. BCNF 한 단락, 무손실 분해(JOIN으로 원래대로)
  7. 정규화 = "하나의 사실은 한 곳에"
- **배치**: S(시작하기 전에) → S(엑셀 수강 명단 비유) → C(중복 표 만들기) → S(갱신 이상) → C(한 줄만 고쳐서 교수가 둘) → S(삽입 이상) → C(오류 예시: 수강생 없는 과목 넣기) → S(삭제 이상) → C(마지막 수강생 지우면 과목도 사라짐) → **F1**(세 가지 이상) → S(함수 종속) → **F2**(종속 화살표) → S(1NF) → **F3**(한 칸에 여러 값 → 행 나누기) → S(2NF) → S(3NF) → **F4**(분해 결과: 학생 · 학과 · 과목 · 수강) → C(정규화한 표 만들고 JOIN으로 원래 표 복원) → C(교수 바꾸기는 한 줄) → S(BCNF) → 표(정규형 요약) → S(정리)
- **퀴즈 vs 코드**: 코스 끝(sq-10-2)에서.
- **그림**: F1 이상 현상 3종, F2 함수 종속, F3 1NF, F4 분해 결과 ERD
- **원본**: 03-2 §8 함수 종속, §10 이상 현상 예제(수강 표), §11 정규형 표, §12 자주 하는 실수

## sq-10-2 일부러 합치기: 반정규화와 분석용 테이블

- **목표**: 정규화의 대가(JOIN 비용)를 이해하고, 반정규화 기법과 위험, 분석용 설계(스타 스키마)를 설명할 수 있다.
- **알아야 할 개념**
  1. 정규화의 비용: 질문 하나에 JOIN 여러 번
  2. 반정규화 = 읽기 속도를 위해 일부러 중복을 허용
  3. 기법: 중복 열, 집계(요약) 테이블, 테이블 합치기
  4. 위험: 원본과 사본이 어긋남 → 갱신 규칙이 필요
  5. 순서: 정규화 먼저, 측정 후 꼭 필요한 곳만
  6. OLTP(주문 처리) vs OLAP(분석) 데이터베이스
  7. 스타 스키마: 팩트 표 + 디멘전 표 (BI · Tableau가 읽는 구조)
- **배치**: S(시작하기 전에) → C(채널별 매출: JOIN 필요) → S(반정규화) → C(중복 열: orders_wide 만들기) → C(원본만 바뀌면 어긋남) → R → C(집계 테이블 CREATE TABLE AS) → S(집계 테이블 장단점) → 표(기법 · 예 · 위험) → S(OLTP vs OLAP) → 표 → S(스타 스키마) → **F1**(스타 스키마) → **F2**(정규화 ↔ 반정규화 저울) → S(정리)
- **퀴즈 vs 코드**: 퀴즈 3 (choice 2NF가 없애는 것 / ox 반정규화는 설계 처음부터 / choice 이상 현상 이름)
- **그림**: F1 스타 스키마, F2 저울
- **원본**: 03-4 §11 정규화와 반정규화 · 반정규화 방법 표, 03-2 §15 실무 사례. 스타 스키마 · OLTP/OLAP는 03-1 OLAP 절을 바탕으로 새로 씀

## sq-11-1 테이블 만들기: 자료형과 제약조건

- **목표**: 물리 모델을 CREATE TABLE로 옮기고, 제약조건으로 잘못된 데이터를 막을 수 있다.
- **알아야 할 개념**
  1. SQL 명령 네 가족: DDL · DML · DCL · TCL
  2. CREATE TABLE 문법, 자료형(INTEGER · REAL · TEXT, MySQL 자료형 대응), SQLite 타입 친화성
  3. 제약조건: NOT NULL · UNIQUE · PRIMARY KEY · FOREIGN KEY · CHECK · DEFAULT
  4. 무결성 세 가지: 개체 · 참조 · 도메인
  5. ON DELETE CASCADE / 기본(막기)
  6. ALTER TABLE(열 추가 · 이름 바꾸기) · DROP TABLE
- **배치**: S(시작하기 전에) → **F1**(SQL 명령 네 가족) → S(CREATE TABLE) → C(동아리 표 만들고 넣고 보기) → S(자료형) → 표 → C(타입 친화성: INTEGER 열에 글자) → S(제약조건 = 문지기) → C(오류 예시 NOT NULL) → C(오류 예시 UNIQUE) → C(오류 예시 CHECK) → C(DEFAULT) → S(외래키) → C(오류 예시 FK) → C(ON DELETE CASCADE) → **F2**(무결성 세 가지) → S(ALTER · DROP) → C(ALTER ADD COLUMN) → S(정리 표)
- **그림**: F1 명령 네 가족, F2 제약조건 문지기
- **원본**: 03-3 §2 명령 분류 · §8 테이블 생성 예 · ALTER · DROP, 03-1 §11 무결성, 03-4 §2 물리 설계

## sq-11-2 데이터 넣고 고치고 지우기: INSERT · UPDATE · DELETE

- **목표**: INSERT · UPDATE · DELETE로 데이터를 바꾸고, WHERE를 빠뜨리는 사고를 막는 습관을 익힌다.
- **알아야 할 개념**
  1. INSERT: 열 이름 쓰기, 여러 행, INSERT … SELECT
  2. UPDATE … SET … WHERE, 계산으로 고치기
  3. DELETE … WHERE
  4. WHERE 빠뜨림 = 전체 변경. 먼저 SELECT로 확인하는 습관
  5. DELETE · TRUNCATE · DROP 비교
- **배치**: S(시작하기 전에) → S(INSERT) → C(dept에 부서 추가) → C(여러 행) → C(INSERT SELECT: 퇴사자 보관 표) → S(UPDATE) → C(11번 부서 연봉 10% 인상) → S(WHERE 빠뜨림) → C(WHERE 없는 UPDATE) → **F1**(SELECT로 먼저 확인 → 같은 WHERE로 UPDATE) → S(DELETE) → C → 표(DELETE · TRUNCATE · DROP) → S(실습 데이터는 매번 원래대로) → S(정리)
- **퀴즈 vs 코드**: 퀴즈 3 (write: 아산공장 부서 연봉 500 인상 후 조회 / choice: WHERE 없는 DELETE / ox: 외래키 막힘)
- **그림**: F1 안전한 변경 순서
- **원본**: 03-3 §7 안전한 데이터 변경, §11 DELETE · TRUNCATE · DROP

## sq-12-1 모두 되거나, 모두 안 되거나: 트랜잭션

- **목표**: 트랜잭션으로 여러 변경을 하나로 묶고, COMMIT · ROLLBACK과 ACID를 설명할 수 있다.
- **알아야 할 개념**
  1. 계좌 이체: 빼기와 더하기 중 하나만 되면 안 된다
  2. BEGIN · COMMIT · ROLLBACK
  3. 제약 위반이 나면 ROLLBACK으로 되돌린다
  4. ACID: 원자성 · 일관성 · 격리성 · 지속성
  5. 동시에 여러 명: 잠금(lock), 기다림
  6. 자동 커밋
- **배치**: S(시작하기 전에) → S(계좌 이체 비유) → **F1**(이체 중간에 멈추면) → C(트랜잭션 없이: 빼기만 되고 더하기 실패) → S(BEGIN · COMMIT · ROLLBACK) → C(ROLLBACK) → C(COMMIT) → C(CHECK 위반 → ROLLBACK) → S(ACID) → 표 → S(동시성 · 잠금) → **F2**(좌석 예매 잠금) → S(자동 커밋, 분석가에게 필요한 습관) → S(정리)
- **그림**: F1 이체 실패, F2 잠금 타임라인
- **원본**: 03-1 §7 트랜잭션 처리 · §11 ACID, 03-3 §10 트랜잭션 제어 예, 03-4 병행 제어와 로킹

## sq-12-2 빨리 찾고, 이름 붙여 두기: 인덱스와 뷰

- **목표**: 인덱스가 검색을 빠르게 하는 원리와 비용을 알고, 실행 계획으로 인덱스 사용 여부를 확인하며, 뷰로 쿼리에 이름을 붙일 수 있다.
- **알아야 할 개념**
  1. 인덱스 = 책 뒤 찾아보기. 없으면 처음부터 끝까지(Full Scan)
  2. B-Tree 그림
  3. CREATE INDEX, EXPLAIN QUERY PLAN: SCAN vs SEARCH
  4. 복합 인덱스 순서(전화번호부)
  5. 인덱스를 못 쓰는 조건: 열에 함수, 앞이 %인 LIKE
  6. 비용: 공간, 쓰기 느려짐, 값 종류 적은 열
  7. 뷰: 저장된 SELECT, 재사용 · 보안, 구체화 뷰
- **배치**: S(시작하기 전에) → S(찾아보기 비유) → **F1**(Full Scan vs B-Tree) → C(EXPLAIN QUERY PLAN: SCAN) → C(CREATE INDEX 뒤 SEARCH) → R → S(복합 인덱스) → C(앞 열 없이 → SCAN) → S(못 쓰는 조건) → C(substr로 감싸면 SCAN) → S(비용) → 표 → S(뷰) → C(CREATE VIEW + 조회) → C(뷰로 보안: 연봉 뺀 명단) → S(구체화 뷰 · 물리 설계 정리) → S(트랙 마무리)
- **퀴즈 vs 코드**: 퀴즈 3 (ox 인덱스 많을수록 좋다 X / choice 인덱스 못 쓰는 조건 / ox ROLLBACK)
- **그림**: F1 Full Scan vs B-Tree
